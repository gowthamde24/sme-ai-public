# Runbook: the real-stack end-to-end run (`make e2e-local`, job BE)

One command drives the **real web**, the **real API** and the **local Supabase stack with Storage** through a real browser, the way a person would, and says PASS or FAIL for each step. It uses **its own ports (web 3002, API 8002)** and **its own throwaway account and workspace** (`e2e-<stamp>`), so the owner's demo (3000, 8000, the demo workspace) is never touched. Everything is invented; **nothing leaves this machine** (the only channel is the API's local stand-in).

## Run it
```
make agent-db-up         # the AGENT stack, with Storage (once; job BG: the run never touches the owner's stack, docs/runbooks/two-local-stacks.md)
make e2e-local
```
It needs Docker, the Supabase CLI, the API's virtualenv (`make install`; Pillow is a declared dependency of the API), Node, and a browser (the first time: `cd e2e && npm ci && npx playwright install chromium`).
What it does, in order: refuses unless the ports are free (never 3000, 8000, 8001) and the stack, including Storage, is up; starts the API (`AGENTS_ENABLED=true`, the scripted model) and the web, recording their PIDs; runs `e2e/be-stack.mjs`; stops **only the processes it started** (by PID and their children); removes the throwaway workspace and account (`e2e/cleanup-be.mjs`). Set `E2E_KEEP=1` to keep the workspace to look at it, `E2E_SHOTS=dir` to choose where the screenshots go (default `e2e/shots-be/`, git-ignored). Exit code 0 only if every step passed.

## Things to know
* **Quiet hours.** The outbox holds messages from 21:00 to 09:00 India time (the default). The run reads the real clock: at night an approved message is **held for the morning** (the run checks the Scheduled tab, the "Held for the morning" history line and the "1 held for the morning" dispatch sentence); in the day it checks that the message is **Sent** by the fake channel. Both branches are in the script; the summary says which one ran.
* **The scripted model has a catalogue path** (job BG): when the question is about sarees, photos, colours or fabrics it looks the sarees up (`find_catalogue_items`, with a colour or fabric if the question names one) and its answer cites the saree it found. H2 therefore asks the real Ask box "Show me a maroon saree" and clicks the saree link in the real answer; there is no stand-in. The real model path needs a model key.
* **The agent database is shared between agents.** An integration or pgTAP session on the agent stack pins its database-wide clock and `make db-reset` rebuilds it. The run **refuses to start** while a test session is alive or the clock is pinned, and says so. Run it when nothing else uses the agent stack. (The owner's demo database is a different stack and is not involved.)
* **The clean-up has a safety lock (job BF).** `e2e/cleanup-be.mjs` switches row guards off, so it **refuses** (exit 2, before any query) unless every database address it can see (`SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, the usual database URL/host variables, the container it talks to) is this machine (`localhost`, `127.0.0.1`, `::1`, the Docker host, the local `supabase_db_*` container), and refuses if any workspace it would delete has a slug that does not start with `e2e-`; the SQL repeats the slug check and fails the whole transaction. `apps/web/scripts/e2e-cleanup-guard.test.ts` pins this (look-alike hosts such as `localhost.example.com` are not local).
* **Clean-up** (`e2e/cleanup-be.mjs`) deletes only workspaces named `E2E Silks ...` with a slug starting `e2e-` and accounts `e2e-*@e2e.example.test`. The app never deletes a workspace (append-only audit), so the script switches the row guards off inside one transaction for those rows alone. The photo **files** stay in the local Storage volume (Storage refuses to delete them from SQL): a few small synthetic pictures.
* **Not in CI.** It needs Docker, the whole local stack, Storage and a browser. Whether it can run in CI without secrets has not been tried; it would need the CI job to `supabase start` (which the integration groups already do) and a browser.

## Job CC: the screens for the new APIs (steps CC1 to CC7)

`e2e/cc-steps.mjs` holds seven steps: **CC1** Settings > Data (a spreadsheet import with mapping and preview, a second import refused as duplicates, a CSV export, the calendar address made, rotated and stopped), **CC2** Settings > Privacy (a real export zip downloaded from Storage, the consent list, the only owner refused, the workspace deletion scheduled and cancelled), **CC3** Find retailers (a real search; two cards are served by the browser's route and saved through the real `places/confirm`), **CC4** Team (an invitation, a second real account joins from the link, a role change, a removal), **CC5** WhatsApp (Connect through its four states, a customer chat, approve, reply), **CC6** GSTIN (the shop's, a customer's, the new-customer form), **CC7** a viewer meets every new screen and the real API refuses them too. Each draws the page at 360 px in the dark and checks targets, text size, sideways scroll and axe.

* **A targeted run:** `E2E_ONLY=CC make e2e-local` runs the sign-up and sign-in steps (A*), the steps whose id starts with `CC`, and the console check (Z1). `E2E_ONLY=CC,Q` adds the Help steps. Without it everything runs.
* The API of this run starts with `PLACES_PROVIDER=fake` (its own fixture map search) and a synthetic `WHATSAPP_ACCESS_TOKEN` (so a WhatsApp number can reach "connected"; the outbox adapter stays the fake and nothing leaves the machine). `scripts/e2e-local.sh` sets both.
* A WhatsApp phone number ID belongs to one business only, so the run uses a fresh one each time. `cleanup-be.mjs` also clears the `integrations`, `privacy` and `team` schemas.

## Job CL: the business-type sign-up (`make e2e-packs`)

`e2e/cl-signup.mjs`, started by the same `scripts/e2e-local.sh` (`E2E_SCRIPT=cl-signup.mjs`), with `AUTH_GOOGLE_CLIENT_ID` and `AUTH_FACEBOOK_APP_ID` set to **public placeholders** so the API offers the two buttons (the local Auth server has both providers off, which is what the run checks). For each business type the API lists (`GET /v1/packs`) it drives: the two-step sign-up by e-mail (cards in the API's order, the terms line, no tick box), the e-mail confirmed in the local database, sign-in, **the setup making the business by itself** with the chosen kind, Today in the type's words and with its checklist and the example-data offer, a typed address to a part the type does not have (the 403 page; for a write the API's `403 module_off`), the Start page (name and city), loading and removing the example data, the second step from the checklist (enrol, sign in with the code), Settings → Fields (add a field, rename it, make it required) and a customer saved with its value. Then the provider paths that need no account of the owner's: **Continue with Google** while the Auth server has Google off (back to step 2 with one sentence, nothing created), and an account made the way Google leaves one (provider `google`, verified address, no sign-up metadata): **with** the kind remembered in the browser (the setup makes the business by itself) and **without** (the setup asks). The terms are checked to be recorded by the setup in both.

* **A real Google or Facebook round trip is NOT run**: it needs the owner's Google and Meta apps and keys (`docs/runbooks/social-sign-up.md`).
* **The throwaway workspaces are renamed** by the run to `E2E Silks <stamp> <label>` with an `e2e-` slug (local database only) so `cleanup-be.mjs` can find them; the sign-up itself names a business "My business". The clean-up refuses to run while any `e2e-` workspace has another name, so a step that renames a workspace must keep the `E2E Silks` prefix.
* `make e2e-local` (the classic run) starts with the same two-step sign-up; a workspace made at sign-up shows the **checklist**, not the saree shop's first-run wizard of the J steps, so step A3c puts the throwaway workspace in the state of one made without choosing a business type (`source = default`).
* **Same shared database rule**: the run refuses to start while another session tests on the agent stack and **aborts** (exit 4, "not a fault of the product") if one starts under it; a pgTAP run restarts the database container.
