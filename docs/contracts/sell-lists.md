# Contract: "What you sell" lists (C1 -> C2), 28 Nov 2026
Status: built on a branch (slice 2 of reports/what-you-sell-lists-design.md); API flag `WHAT_YOU_SELL_LISTS` (404 on every route while off). Tables: migration 20261231990000.

A **list** has a name, a kind, columns and items (rows). The existing catalogue and the four fixed styles are not listed here yet (slice 4 adds them as built-in lists).

## Routes (prefix `/v1/tenants/{t}/lists`; Owner or Admin write, with the second factor when they turned the authenticator on; every member reads)
* `GET ""` -> `{lists: [{id, name, kind, is_main, row_count, columns: [{key, label, type, choices, role, billing_period, quote_default}]}]}`
* `POST ""` `{id (the web mints it once per opening: the same id again is a retry), name 1..60, kind}` -> 201 the list with the kind's default columns. kind: products, digital, services, bookings, courses, subscriptions, rentals, food, events, other.
* `GET /{id}`; `PUT /{id}` `{name, make_main}`; `POST /{id}/remove` -> `{removed: true}` (its items go with it).
* `PUT /{id}/columns` `{columns: [{key?, label 1..40, type, choices? (type choice: 1..20 words), role?, billing_period? (price only; default one_time), quote_default?}], confirm?}`: the WHOLE ordered set, at most 12. A column with a `key` is an existing one (rename, reorder, change role or choices); without a key it is new (the server makes its key). An existing column missing from the set is hidden; if items hold information in it the call answers `column_has_data` unless `confirm: true` (the information is kept). A column's type can change only while no item holds information in it.
  * types: text, number, rupees (whole paise), yes_no, choice, photo, link (https only), date (YYYY-MM-DD), datetime, duration (whole minutes).
  * roles: `price` (type rupees; SEVERAL allowed, each with its own label and `billing_period` one_time | per_month | per_year | per_hour | per_day | per_unit | from; exactly ONE has `quote_default: true`, the first is made the default when none is named), `availability` (type choice), `quantity` (number), `how_to_buy` (link), `description` (text): one column each (`role_taken`)., and `category` (type choice, ONE per list; round 2, 26 Nov 2026): the item's kind in one word ("Blouses", "Silk"). The phone assistant says it with the item: the pack's item lines read `Silk piece (Blouses): In stock. ...` and a price line reads `Silk piece (Blouses), Price: Rs 450`. A `category` column that is not a choice answers 422 `validation_error`; a second one answers 409 `role_taken`.
* `GET /{id}/rows?limit<=50&cursor&q` -> `{items: [{id, name, cells: {<column key>: value}, active}], next_cursor}`.
* `PUT /{id}/rows/{row_id}` `{name 1..120, cells, active}` -> 201 new / 200 the same id again. A cell must fit its column (text <= 200 characters; number; rupees: a whole number of paise from 100; yes_no true/false; choice: one of the column's words; link: https; date; duration 1..525600). **Only the Owner sets or changes a rupee amount** (an Admin saving a price gets 403).
* `POST /{id}/rows/{row_id}/remove` -> `{removed: true}`.

## Starter lists (round 2, 26 Nov 2026; behind the same flag)
* `POST /v1/tenants/{t}/lists/starters` (Owner or Admin, with the second factor when they turned the authenticator on; no body) -> 200 `{created: [names], already_there: [names], skipped_cap: [names], lists: [...]}` (`lists` is what `GET ""` answers). It makes the starter lists of the workspace's industry pack that do not exist yet (matched by name without regard to case), in order, as many as the list cap allows (8 on a trial, 10 paid; `skipped_cap` names the ones with no room); a second call makes nothing twice. The first list made in an empty workspace is the main one. A workspace whose pack has no starters answers `created: []`.
* The textiles pack starts with: **Sarees**, **Dress materials**, **Blouses**, **Dupattas** (kind products: Price, Category, Availability, Quantity, Photo), **Fabric by the metre** (products; its price column is "Price per metre", period `per_unit`) and **Stitching and alterations** (services: Price, Category, Time, Description). Each has a `category` column with a few starting words that the owner renames freely. The data is the table `sell_list_starters` (migration 20261231992710): another pack gets starters with a data migration, no code.

## Closed refusals (`error.code`, also in `error.reason` and `error.fields`); plain sentences are the API's `message`
409: `list_limit` (10 lists, 8 on a trial), `column_limit` (12), `row_limit` (1,000), `name_taken` (a list, a column or an item of that list), `one_default_price`, `role_taken`, `column_has_data`. 422: `value_not_allowed`, `not_a_price`, `validation_error` (a shape the API does not take: unknown kind, role, type or period; a cell key that is not a column slug). 403 `forbidden`, 404 for a list or item that is not this workspace's or while the flag is off.

## What the assistants may do with a list (slice 4; stated now so screens do not promise more)
Amounts come only from `price` columns with an exact value; a `from` period is never spoken as an exact amount; each amount is named with its column's label and period. `how_to_buy` links may be shared when the caller asks; a paid download or access link is NEVER sent by the assistant and delivery stays outside it. A missing fact is "I will ask the owner".

## Import into a list (slice 3)
* `POST /lists/{id}/import/preview` `{file_id (the assistant's file route), mapping? {heading: column key | "name" | null}}` (Owner or Admin) -> `{mapping, rows: [{name, cells}], notes: [{code, row?, column?}], unclear}`. Nothing is saved. The headings of the file are matched to the list's columns: the `mapping` you send first; else a remembered one whose headings are (nearly) all in the file; else the column's own label, then plain words for each role (price words go to the default price column unless the heading names another price column; stock/availability, qty, description, link). `mapping[heading] = null` means the column is left out; the screen shows each heading with a dropdown of the list's columns and "leave out".
* Cells are converted to what their column holds: rupees (`Rs. 1,250`, `₹900`, `450/-` -> whole paise), number, yes/no (yes, y, true, 1 ...), choice (matched to the column's words without regard to case), date (`2026-12-01` or `01/12/2026`), duration (`90`, `90 min`, `1.5 h`, `1:30`), https link, text (<= 200 characters). A cell that cannot be read is LEFT EMPTY with the note `cell_unreadable` (row, column key): never guessed. Notes (closed): `name_missing` (row), `cell_unreadable`, `too_many` (the first 1,000 rows only), `unreadable` (`unclear: true`: no usable table or no name column).
* `POST /lists/{id}/import/commit` `{rows (at most 1,000: the owner's corrected rows), save_label?, mapping?}` (Owner or Admin; only the Owner when the rows carry a rupee amount) -> 201 `{created, updated}`. All or nothing: one bad cell refuses the whole file with the usual closed reason. A row whose name already exists in the list UPDATES that item (only the cells the file carries; the others stay), a new name is added. With `save_label` and `mapping` the mapping is remembered (10 per list; the same label replaces).
* `GET /lists/{id}/import/mappings` (any member) -> `{mappings: [{label, mapping}]}`.
* A photo or notebook page works the same way through `preview` (the file reader runs local OCR first and the AI model's vision only when that finds nothing, never in a school's workspace; it counts as one assistant run, 429 `ai_limit` when the hour's runs are used).

## Built-in lists and the readers (slice 4)
* `GET /lists` also returns the stores that already exist as READ-ONLY built-in lists (only those that have rows): `builtin` is `catalogue` (Sarees), `services`, `courses`, `properties`, `pricelist` or `quote`; `edit_in` says where the owner edits them (`catalogue`, `what_you_sell`, `price_list`); their `id` is stable per workspace; their `columns` are a fixed, read-only description (prices carry the price role). A built-in list has no rows route here and cannot be changed through `/lists/{id}` (the web sends the owner to the screen named in `edit_in`).
* The phone assistant now also reads the owner's lists: every active item's exact amount in a price column that is not a from-price, said as `<item>, <column label>: Rs N <period>` with the default column marked as the usual price; plus an item's availability word and short description exactly as written. A from-price, a price that is not exact and an item that is inactive are never in the pack. The money guard allows exactly the amounts in the pack.
