Plan and owner decisions: `docs/plans/t010-integration.md` (sections 2.2-6, 8, 11). Related: ADR 0005 (consent ledger), ADR 0013 (option A / B), ADR 0016 (second factor), ADR 0017 (local-first),
ADR 0018 (questions; lock order), ADR 0020 (suppression keys: the gate this part enforces), ADR 0021 (orders: the follow-up stop), `docs/plans/t010-followup-cadence.md` (lane C's pure engine, `packages/pure/followup_cadence` 1.0.0, the contract this wraps).

## Context
Part 1 built the suppression keys. Part 2 is what a person does with them: record what they sent and what the customer said (touches), keep a versioned cadence policy, and get a DRAFT follow-up (and persisted question drafts) that a person reviews, approves, copies and sends OUTSIDE the system.
**Nothing here sends anything, calls a model or a provider.** A touch, a draft and an approval are records. Migrations `20261024090000_t010_part2_followups.sql` and `20261024090100_t010_part2_question_drafts.sql`; pgTAP files 62 and 63.

## Decisions
**1. The gate lives in the database and is repeated at every step.** `app.followup_gate(lead, channel, lock)` is run by `record_touch` (outbound), `create_followup_draft`, `approve_followup_draft` and `record_draft_sent`, each time against the state as it is then (owner review 2026-10-07, requirement 1). Order of the checks (safety first): no contact, erased, suppressed
(SM220, detail `contact` / `erased`), no identifier for the channel, **no stored key for the channel (SM221: missing data never means "not suppressed")**, a suppressed key (SM220, detail `key`, or `erased_key` when an erased marker follows the key's last lift; the public read shows both as `key`), consent not granted or the contact archived (SM220, detail `consent`).
The key kind is part of the check: an e-mail draft reads the e-mail key, WhatsApp and phone read the phone key. With `p_lock` the key's advisory lock is taken in SHARED mode (a suppression that holds the same key waits for the transaction, or has committed): the suppression path (contact for update, then the key's exclusive lock) and this path (contact for share, lead for update, then the key's shared lock) take the same locks in the same order.

**2. The caller names a LEAD; the contact is derived.** The plan had `p_contact_id`; a caller-supplied contact is a way to name a different person than the lead's. The contact is the lead's current contact, locked first; a lead whose contact changed while a function waited (or since a draft was made) is stale (SM224).

**3. The database decides whether the engine would answer `draft_followup`.** The API runs the pinned engine; the database rebuilds the request, as of the database's clock (as_of from 3 minutes back to 2 minutes ahead), (`app.followup_build`, same value as `services/ai-api/app/followups/builder.py`) and refuses any other (SM226), then computes the positive decision itself (`app.followup_blocker`: the flags, a reply, the touch limit, the future-history rejection, the gap and minimum gap after the LAST
outbound touch, the weekday, the recipient's local holiday, quiet hours, wrapping or not). The engine moves a candidate only forward and answers `draft_followup` only when the moved time is not after as_of, so a due draft is due at as_of itself; the whole positive condition is therefore checkable, not trusted. A refusal says why in a closed word (SM225 detail:
`suppressed | replied | closed | max_touches | initial_outreach | future_history | not_yet`), and the engine's result must then be exactly the draft answer for that touch number, request hash and engine version (SM226). WAIT and STOP results are not recomputed (nothing is created for them); the rule trace is stored as given. An equivalence test (the real engine against the database function, generated histories and calendars) pins them equal (commit 2).
This goes one step beyond the plan ("the database does not re-implement the engine"): the predicate is small, and it removes the option-A trust gap for the one thing that matters (a forged "due" result). **The owner accepted it as a deliberate exception (review 2026-10-07)** on these conditions, all of which hold:
(a) the database re-implements ONLY the engine's draft condition (stop rules, touch cap, gap and minimum gap, weekday, holiday, quiet hours); it never computes a wait time, a next-eligible time or a stop result; (b) it is tied to the closed engine-version list: `followup_engine_versions` is written only by migrations, so **a new engine version needs a new migration, which must re-read and, if the rules changed, re-write `app.followup_blocker` and its tests**; (c) it **fails closed**: a request it cannot read (a missing or null input, a wrong shape) is `invalid`, never due (`app.followup_blocker` wraps `app.followup_blocker_inner`; every input the rules read must be present).
**Drift risk.** Two implementations of one rule set can disagree. The consequence is bounded: a database that is STRICTER than the engine refuses a draft the engine would allow (a person sees SM225 and nothing is created); a database that is LOOSER would accept a draft the engine would not make (a draft that an Owner or Admin must still read and approve with a second factor, and that a person must still send by hand). **Gate (commit 2): `tests/integration/test_followup_equivalence.py` runs the real engine against the database function over an exhaustive boundary grid, every rule at n-1, n and n+1 minutes (the gap in days, the minimum gap, the quiet-hour edges on both sides of a wrapping and a non-wrapping window, the hour and weekday edges, a holiday on the local date, the touch cap, every stop and flag combination), plus generated histories; ANY disagreement fails the build.** The engine's version, its golden hashes and this grid move together.

**4. No text from a person reaches a draft.** A draft's wording is a CLOSED template (`followup_templates`, English, migration-extended, no variables) copied by the database; the caller supplies no text. The wording is chosen by touch number (the last allowed touch, the second, every other). The templates are SYNTHETIC placeholders the family replaces (checklist). Question drafts store the API's closed-template text within caps
(8-300 characters, text hygiene, **no contact data** by `app.text_has_contact`, a code from the closed list, a line 0..5); the database cannot re-derive that text from the requirement's fields (limit, below).

**5. Touches.** `record_touch` is a person's record: Owner / Admin / Sales at any assurance level. **An outbound touch obeys the gate** (nobody can record contacting a person the system may not contact); **an inbound touch is ALWAYS recordable** (it can only stop outreach: the engine answers `human_takeover`, and refusing it could keep a cadence alive), and it discards every open draft of the lead (`reply_recorded`).
An outbound touch discards the open drafts for its touch number or an earlier one (`superseded`). **An inbound touch for an ERASED contact is refused (SM220, detail `erased`): erasure wins, no new record about an erased person.** An inbound touch never lifts, shortens or weakens a suppression or a follow-up stop: it writes one touch row and discards open drafts, nothing else (pgTAP C49-C54 compare the contact's suppression and consent, the key ledger, the consent ledger, the stop and the gate before and after).
**The time of a touch** (owner reviews 2026-10-07): null is the database clock (the web form sends null for "now"); a stated time is **never after now** (no future slack anywhere), at most **7 days back**, and **never before the lead was created**; an OUTBOUND touch is also **never before the lead's latest outbound touch** (a reply may be recorded late, "I sent it" may not be recorded out of order); the table itself refuses a touch after its own recording (`occurred_at <= recorded_at`, even for a privileged writer). 500 touches per lead (SM229). Append-only.

**6. Drafts.** One ACTIVE (draft or approved) draft per (tenant, lead, touch number) by a partial unique index. States: `draft -> approved -> recorded_sent`, or `discarded` (a person, or the system: superseded, reply_recorded, suppressed, erased). Approval is the Owner's or Admin's, **with a second factor, after the role is proven**. The approval carries the fingerprint the person reviewed
(`state_hash`, the request without as_of, the contact and the channel); it is refused when that is not the stored one, or when the state moved since (the history, the policy in force, the flags, the contact): SM224. `record_draft_sent` ("I sent it") re-runs the gate and the stop and requires the history to be the one the draft was made for (SM224): an approval that was valid when given is not enough later. **The sent time may not be before the draft's approval, not before the lead's latest outbound touch and never after now** (null is the database clock); **a draft older than 7 days can be neither approved nor recorded as sent (SM224)**.
Touch 1 is a person's (plan decision 12: "the first outreach draft is a person's, from the lead page, with the same suppression and consent gates; the cadence takes over after its recorded touch"): there is no system draft for a lead with no outbound touch (`initial_outreach`); the person writes the message, records the touch with `record_touch` (gated) and the cadence takes over.

**7. Stops.** `app.followup_stopped(lead)`: an archived lead, or an order accepted, declined or cancelled, or a withdrawn quote (`app.order_stops_followups`, the lead's latest order decides): SM227 with the closed reason, at create, approve and record-as-sent (owner review requirement 2).

**8. A contact that becomes suppressed or erased has its open drafts discarded** (a trigger on contacts; the draft rows only). The gate re-checks at every step too, so the trigger removes a draft from the screen; it is not the only line of defence. A key suppressed through ANOTHER contact is caught by the gate, not by the trigger.

**9. The policy** (`followup_policy_versions`): immutable, versioned like the quote policy; Owner with a second factor; effective today or later and never before the latest; typed columns with CHECKs (gaps 0..365 days, exactly max_touches - 1 of them, quiet hours HH:MM with distinct ends, weekdays 0..6 distinct, holidays distinct, offset -840..840 minutes). Weekdays and holidays are stored sorted (the engine request carries them in that order).

**10. SQLSTATEs** SM220 to SM229 (the part 2 family; SM221 shares its code with part 1's erasure refusal, whose message differs): see the migration header. **Reads:** `followup_gate` (blocked / stopped / policy_in_force in closed words, never a key; an erased marker on a key is shown as plain `key`, the write refusals keep the detail `erased_key`) for the screens; the tables are readable by Owner / Admin / Sales through RLS, a Viewer reads none of it.

## What the database proves and what it trusts
Proven: tenant isolation, roles and the second factor (role first), the state machines, one active draft per touch, append-only touches, no client write grants, the gate at every step, the stop at every step, that the request is the database's own, that the draft is due by the engine's own rules, that the result is the draft answer for this request, that no text a person wrote is in a draft.
Trusted: that the HMAC the API recorded is the HMAC of the identifier (option A, ADR 0020: a member who talks to PostgREST could record a wrong key; option B before an external customer); that a person really sent what they say they sent; the question text within its caps; the rule trace as stored.

## Consequences and limits
* The touch time bounds (never after now, 7 days back, not before the lead's creation, an outbound touch not before the latest outbound one) are the database clock's. A web form sends null for "now".
* A key suppressed through ANOTHER contact stays visible to Sales as `key` in the gate (the existing `check_suppression` already answers a boolean per key).
* A "sent" touch is bounded below by the draft's approval and by the lead's latest outbound touch, and above by now; a draft older than 7 days can be neither approved nor recorded as sent (SM224, stale). An ordinary reply may be recorded earlier than the previous touch.
* The question text is the API's word within its caps (decision 4); a member who talks to PostgREST directly can store another closed-looking question for a requirement. Nothing leaves the system.
* Languages other than English (owner question 13) are not built; templates are closed rows, so a language is a migration plus a reviewer who reads it.

## What erasure does to these tables TODAY (answered by `64_t010_part2_erasure.test.sql`)
* **Contact erasure:** `lead_touches` keeps every row, byte-identical, still pointing at the anonymised contact (a business record: direction, channel, time, contact id, recorder; it holds no personal data). `followup_drafts` keeps every row with its content unchanged (the body is a closed template, the request holds timestamps and closed words): an OPEN or APPROVED draft of the erased contact is discarded as `erased` (a system discard by the contact trigger); a draft already recorded as sent stays. No new draft, outbound touch or inbound touch can be made for the erased contact (SM220 erased). Question drafts and policies are untouched. No row of these tables, nor its audit trail, holds the person's name, e-mail or phone (tested with a text search).
* **Workspace erasure (`erase_tenant`):** finishes clean on a workspace holding policies, touches, drafts and question drafts (no registered column lives in these tables, so the append-only trigger never fires); every contact is erased, so every open draft is discarded as `erased`; touches, policies, question drafts and the content of drafts are byte-identical afterwards. **Open question for the DPDP review (checklist row):** these rows are retained after erasure by design; counsel confirms that PII-free business records of what was sent, and when, may stay.
* **A changed e-mail or phone** forgets the stored key of THAT identifier (part 1's trigger); the gate answers SM221 for that channel until the API re-keys it (tested for both identifiers, with a client's own update).

## Commit 2 as built (services and API; no migration)
* **The adapter** `app/followups/cadence_port.py` is the one door to the pinned engine (the pattern of the order lifecycle port): version allow-list, fail closed, fixed errors, the documented hash recomputed on every run, golden vectors by value. **The builder** `app/followups/builder.py` produces the engine request from rows read through PostgREST with the caller's token, equal key for key to `app.followup_build`. The API decides nothing: for a draft it hands the database the canonical request and result and the database runs the gate, the stops and its own due predicate and refuses any difference.
* **Endpoints** (`/v1/tenants/{tenant_id}/...`): `followup-policy-versions` (Owner, second factor), `leads/{id}/touches`, `leads/{id}/followup-drafts`, `leads/{id}/followup` (the gate, the engine's decision now, the touches and drafts), `followups/due`, `followup-drafts[/{id}]`, `.../approve` (Owner or Admin, second factor), `.../discard`, `.../sent`, `requirements/{id}/question-drafts[/sync]`, `question-drafts/{id}/approve|discard`. No request carries wording, a contact, a status or a tenant; a Viewer reads nothing. `occurred_at` null is "now" (the database clock).
* **Errors:** SM220-SM229 map to fixed sentences with a closed `reason` (`app/followups/messages.py`); the public gate shows `key` as the database returns it. Question-draft ids are random (`uuid4`), never derived.
* **The gate (decision 3)** `tests/integration/test_followup_equivalence.py`: Tier 1, 1,949 boundary-grid requests (815 due) against the REAL engine: due-ness agrees in all 1,949; the reason agrees in 1,822; **the 127 others are one divergence, below**. Tier 2, 720 comparisons of the Python-built request with `app.followup_build` (20 leads x 6 policies x 6 times): equal in all.
* **RESOLVED divergence (commit 2b, the commit after `a4b97d7`, migration `20261025090000_t010_part2_blocker_order.sql`).** The gate found that the engine VALIDATES before it applies any rule, so a history entry after as_of is a rejection (FUTURE_HISTORY) even when a suppression flag, a reply or a close would also stop the lead, while `app.followup_blocker` named the stop (112 cases `suppressed`, 12 `replied`, 3 `closed`; due-ness always agreed). **The owner decided the pinned engine is the contract and the database follows it.** The engine's order (`packages/pure/followup_cadence`, `decide()`) is: (1) `_bounded` size and shape limits; (2) `_validate` every field, type and range, ending with the history loop where an entry after as_of is the rejection FUTURE_HISTORY; (3) the rules: do_not_contact / opted_out / bounced, a reply (the flag or any inbound entry), won / lost, the touch cap, no outbound touch (initial outreach), then the gap in days, the minimum gap and the calendar (weekday, holiday, quiet hours). `app.followup_blocker_inner` now runs: unreadable input (`invalid`), future history, suppressed, replied, closed, max_touches, initial_outreach, not_yet. One function replaced, one block moved (pinned by `tests/test_migration_copies.py`); pgTAP 65 pins the order on both sides of every boundary and the safety of the refusals; the gate now requires agreement on due-ness AND reason in all 1,949 cases and the 720 builder comparisons stay equal.
* **Commit 2b additions.** (1) PRIVACY: a client is never told `erased_key` (that another person who shared the identifier was erased by right): `errors.CLIENT_REASON` maps it to `key`, with the sentence of `key`, before it reaches the response; the typed exception keeps `internal_reason = erased_key` and the server's log line names it (the Owner's lift screen needs the distinction; a client does not). The public gate read already said `key`. (2) The lead page (`GET /leads/{id}/followup`) no longer fails whole when the engine cannot run: it returns the gate, the touches and the drafts with `decision: null`; creating a draft and the due list stay fail-closed (503 / 502). (3) The policy the Python repository picks (`active_policy`: the latest `effective_from` on or before the date, the higher version number winning a tie) is pinned equal to `app.followup_active_policy_version` at seven dates by `tests/integration/test_followup_policy_selection.py`. (4) The equivalence gate carries no exclusion: 1,949 of 1,949 grid cases agree on due-ness AND reason, and 720 of 720 builder comparisons are equal.

## Commit 4b (2026-10-07): a stopped lead is never due, and the unkeyed sentence is honest
* **Layer changed: the API service (`app/followups/service.py`), not the engine and not the database.** `followup_cadence` 1.0.0 stays pinned and unchanged. The engine knows a lead's touches, flags and the policy; it does NOT know about orders, withdrawn quotes or an archived lead. Those stops are the DATABASE's (`app.followup_stopped`, SM227), so for a lead with an accepted order the engine said `draft_followup` / `eligible_now` while the database would refuse the draft: the lead page showed guidance that a draft can be made and the due list showed "Due now". The fix puts the stop where it belongs: (1) `lead_followup` reads the gate FIRST; when `gate.stopped` is set the engine is not asked and the decision is `stop` with the stop reason as `reason_code` (`terminal` true, no touch number, `engine_version` `"none"`: the database's rule produced it, not an engine); (2) `due_list` leaves out every lead whose gate says stopped. The creating of a draft is unchanged (the database refuses a stopped lead, SM227, as before). The web adds a second line of defence: a lead page whose gate says stopped shows the stop line and no guidance, whatever decision it was sent.
* **Not changed (reported, for the owner's decision):** a lead BLOCKED by the gate has the same shape of defect. VERIFIED on the real stack: a lead whose phone number is shared with a suppressed contact reads `gate.blocked = key` while the engine still answers `draft_followup` and the due list lists it as due (the draft is then refused, SM220 `key`). By reading the code the same holds for consent withdrawn after a touch and for an erased contact: the engine sees only the lead's own suppression flag, not keys or consent. An UNKEYED contact cannot reach this state (recording an outbound touch for it is refused, SM221), and an opted-out contact reads `stop` from the engine's own flag (lead 4 of the rehearsal). The fix would be the same as for stops (the gate decides, the engine is not asked); it needs one gate read per candidate in the due list.
* **The sentence for SM221** said "The owner can record the keys first", but no screen lets the Owner do that (the endpoints `POST /suppression/backfill` and `GET /suppression/status` exist, nothing in the web calls them). It now says "Recording keys for existing contacts is not available on any screen yet." (`messages.py` and `followup-text.ts` change together; the Python pin test compares them). The missing screen is a row of `docs/pre-pilot-checklist.md`.
