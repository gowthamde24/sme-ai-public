# ADR 0075: privacy rights (download my data, delete my account or workspace, retention, grievances, re-accept)

Status: ACCEPTED for the local stage (job BN, 2026-10-12). Nothing is deployed. Migrations `20261116090000_bn_exports_and_deletion.sql` and `20261116090100_bn_retention_and_grievances.sql`; pgTAP `85_bn_privacy_rights`; code in `services/ai-api/app/privacy/`.
Base: this job was built on the branch `api/bi-integrations` (it needs BI's `integrations.policy_acceptances`), not on `main`. Rebase it after BI is merged.

## Context

India's Digital Personal Data Protection Act, 2023 gives a person the right to access their data, to have it corrected and erased, to withdraw consent and to have a grievance heard, and it expects a data fiduciary to keep personal data only as long as needed. The product holds two kinds of personal data: the people who USE it (shop staff: an account, a chat with the assistant, the trail of their actions) and the people the BUSINESS deals with (customers). The first group are the product's users; the second group's data belongs to the business (a "data fiduciary" in its own right), and the product is its tool. This ADR builds the machinery for both without inventing legal advice: what the law requires the owner must confirm with a lawyer in the DPDP review (T012).

## Decisions

1. **Policy re-accept (small).** The terms and the privacy notice keep their separate versions (BI). New: each can carry an effective date (`TERMS_EFFECTIVE_FROM`, `PRIVACY_EFFECTIVE_FROM`; empty = at once) and a switch `POLICY_ENFORCE` (default OFF). When on, every workspace route refuses a person who has not accepted a binding version with `403 policy_acceptance_required`; the check runs after the role check (a stranger still gets 404, a lower role 403) and the routes a person needs in order to read and accept (`/v1/me/*`, `/v1/policies/*`, `/v1/account/*`) never pass through it. A "yes" is remembered for 60 seconds in memory, a "no" never. Off by default because switching it on locks out everyone until they accept: the owner chooses the day.
2. **Download my data.** An asynchronous export: a row in `privacy.data_exports` (queued, running, ready, failed, expired), made by the API in a background task with the PERSON's own token, put in a private Storage bucket `exp-<user id>` and handed out only as a Storage signed URL that works for **5 minutes**. The file lives for **24 hours**; the worker deletes it (and marks the row only after Storage confirmed, `remove_checked`). Two scopes: *person* (what the ACCOUNT holds about the signed-in person: profile, roles, accepted versions, calendar feeds as dates, the trail of their own actions without values, their own assistant chat, their exports and deletion requests; any member) and *workspace* (every business table, read with the OWNER's token so row-level security decides what is in it; Owner + second factor). The workspace list is a constant, and an integration test fails if a table with a `tenant_id` is missing from it. Audited (`data_export.requested|ready|downloaded`), no file name or hash in the audit. At most one open export per person, five a day; an export that never finished is given up after 30 minutes. Format: JSON files and a README in a zip (open, machine-readable); the size limit is the bucket's 50 MB.
3. **Deleting an account.** Any member may request it (typing their own e-mail; an Owner or Admin needs the second factor). Refused (`sole_owner`) while they are the only Owner of any workspace. 14-day cooling-off, cancellable, one open request per person. After it, the AW worker deletes the `auth.users` row (the profile, memberships, sign-up records, feeds and acceptances cascade), writes an `account.deleted` audit event in each workspace they belonged to (the audit rows stay: they are the business's record, with an actor id that no longer resolves), clears the id from grievances they wrote, and expires their export files. A request whose person became the only Owner of a workspace meanwhile is **blocked** (not executed). Decision: the audit trail keeps the actor's id; it is an opaque uuid once the account is gone.
4. **Deleting a workspace.** The Owner (second factor) types the workspace name. The EXISTING tenant erasure request (`public.request_erasure`) is made at once, with the same id, so its own 24-hour wait runs inside the 14-day cooling-off; nothing is erased until the Owner, after the cooling-off, calls `execute` (`public.execute_erasure`, unchanged). Cancelling cancels both. Grievance text of the workspace is cleared by a trigger when its erasure executes. We reuse the existing erasure functions rather than write a second deletion path; a tenant's rows are anonymised, not dropped, as ADR 0014 decided.
5. **Retention.** Per workspace, in days, nullable (null = keep, no row = nothing purged): chats 30-3650, voice transcripts 7-3650 (never longer than chats), enquiries 90-3650, scheduler rows 30-3650, audit rows 365-3650. Only the Owner (second factor) sets it; a preview counts what the next clean-up would touch. The worker's `privacy_worker_run_retention` (at most once an hour per workspace) replaces text by the erasure tombstone `erased:1` through the existing `app.erase_column` (rows, dates and numbers stay) and DELETES scheduler and audit rows older than the age. The only door for those deletes is `app.retention_purging()` (a setting that only a definer function owned by the database owner sets inside its own transaction); audit rows and scheduler rows stay append-only for everyone else. `app.erasure_running(tenant)` also opens (for that one workspace, in that transaction) for the retention clean-up so the same tombstone triggers accept it. A voice transcript is a user message whose run carries a `voice-stt` cost reservation. Not covered: the outbox (messages to customers are the business's record), orders, quotes, evidence.
6. **Grievances.** `privacy.grievances`: kind (access, correction, erasure, withdraw_consent, complaint, other), subject, details, an "on behalf of a customer" flag with optional name and contact, status received, acknowledged, in progress, resolved or rejected (a closing note is required), due in 30 days (shown as overdue), a trail of events. Any Owner, Admin or Sales member submits; Owner and Admin work them; Sales see only their own. This is the intake and the tracking. It is NOT a public form for customers (that needs the hosted site and the owner's published contact); the Owner logs a customer's request "on behalf". Ten a day per person.
7. **The worker.** `Housekeeping` runs after each tick (at most every 5 minutes), independent of the outbox switches: account deletions, expired export files, retention. A failing step is counted and the next still runs; a refused token ends the pass.

## Errors

SQLSTATE → API: `SM611` 409 `sole_owner`, `SM612` 409 `cooling_off`, `SM613` 409 `privacy_state`, `SM614` 429 `privacy_rate_limited`, `SM615` 422 `confirmation_mismatch`, `SM306` 403 `mfa_required`, `23503` 404, `42501` 403. No data-layer text reaches a client.

## Consequences and open points

* The account deletion removes the account, not what the person typed into the business's records (a note on a lead, a chat reply a customer received): those are the business's. The person-side file says so.
* A signed link is a bearer URL for five minutes; anyone holding it can download. Short life, no-store, audited.
* Backups are outside deletion and export; the hosted plan (ADR 0072) must say how long backups live (T012, the DPDP review).
* Not built (owner/lawyer decisions): a public grievance form and the named Grievance Officer contact, consent-manager integration, breach notification, children's data rules, the legal text of the terms and the notice, a retention default.
* `POLICY_ENFORCE` should be switched on only when the web has the accept screen (Claude 2: `GET/POST /v1/me/policy-acceptances` and the `403 policy_acceptance_required` handler).
