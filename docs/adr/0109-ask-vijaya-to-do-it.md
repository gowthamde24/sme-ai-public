# ADR 0109: "Ask Vijaya to do it", the tasks engine (job DR, part B1)

Status: built on branch `api/dr-tasks` (night run 27 Oct 2026), stacked on `api/ds-spoken-style` (#118) and the night-3 branches. Telephony does not exist: every result is simulated.

## Decision
1. **One instruction, one plan, one approval.** The owner types or says an instruction (any of en, te, hi, kn, ta, ml). `POST /tasks/plan` returns a Task: the people, the channel (call, WhatsApp, both), the goal, the questions to ask (each with a key and a type), script notes, a time window, the estimated cost, a follow-up, and a plan hash. The owner reviews it, may exclude people, and approves ONCE for everyone left in (`POST /tasks/{id}/approve`, Owner with a second factor, bound to the hash: any change to who is in sends it back to `planned`).
2. **Claude describes, code decides.** The planner is a run of the assistant like any other (switches, limits, the worst-case cost reserved before every call and the real usage recorded; the model is the one `AI_JOB_ASK` names, Claude by default; Sarvam is refused for it). It has two small tools to look (count the leads of a segment; find a contact by name: first names only) and one structured answer. **It describes the people** (a segment, or a name); `app/tasks/resolver.py` finds them among the workspace's OWN leads and contacts with the caller's token. It never sees a phone number or an id, and a number in a list the owner provides that matches no contact is reported as unmatched and never contacted. **It never calculates a price**: the estimate, the cap and the cheapest-supplier answer are computed by code from counts and captured amounts.
3. **Unclear means ONE question.** If the instruction does not say who or what, the plan is a single clarifying question in the owner's language; after the answer a plan is made from what there is (a second question is never asked).
4. **Safety rules in code and in the database.** Only own contacts; a stopped (STOP), erased or archived person, or one with no phone, is skipped with a closed reason; every call opens with the AI disclosure (the dialer interface requires it, the runner checks it); a plan that hides the AI, puts a figure or a promise in the WhatsApp text that the owner or an approved fact did not give, or is in the wrong language is asked again and then refused; **schools: no payment reminder and no fees, marks or dues in any goal, question or message** (the planner refuses, the database refuses again: SM951); a **promotional** template (offer or event invite) goes only to people whose WhatsApp consent is granted and only by WhatsApp until a 140-series number exists.
5. **Run through what exists, all fake.** WhatsApp messages are ordinary outbox messages (the approver's token, a deterministic id per task and person so a retry never sends twice, category `followup`): the outbox's own rules still decide (opt-in, quiet hours, daily limit, content flags, kill switches, "held for a person"). Calls go to a `Dialer` interface whose only implementation is a FAKE: deterministic simulated conversations, never dialled, never stored as outcomes of real customers. The cost is counted with fake rates (Rs 1.50 a minute, Rs 0.60 a message); the default cap is the estimate plus 20 percent; at the cap the database pauses the task (a Needs-you item) and only the Owner can raise it.
6. **The report: short answer first.** `GET /tasks/{id}/report`: "Cheapest: Sri Venkateswara Traders ₹395, Thursday" (the lowest captured amount, found by code) or "5 of 8 reached, 3 interested", then one row per person with outcome, captured fields, transcript and a recording link (null until telephony exists).
7. **Seven templates** as data (`data/templates.json`): call new leads, re-engage old leads, confirm appointments, collect feedback, payment reminder (not schools), supplier price enquiry, offer or event invite (promotional).
8. **The knowledge base is an interface** (`KnowledgeBase.approved_facts`): the tasks engine states only approved facts and the owner's own words; `NoKnowledge` (nothing approved) is wired until part A1's table is.
9. **Everything the owner said is personal data:** the instruction, the plan text and the transcripts are in the erasure registry and the data inventory, out of the audit trail, and never in a log.

## Consequences
- The run happens in the API process under the approver's token (a background task after `approve`); a token that expires mid-run stops it and `POST /tasks/{id}/run` continues (claims stuck for five minutes are taken back). A worker-driven runner is the next step once telephony needs one.
- Evaluations: `make tasks-eval` (Claude Haiku only, 500,000 tokens at most) plans 30 synthetic instructions in six languages; results in `~/Desktop/stack19-jobs/model-compare/tasks-eval.md`.
- Live findings that shaped the planner (first run: 167 of 183 checks): the model sometimes sends an empty or doubled selector (`{}`, or a segment and a name), which is now tidied instead of failing the plan; questions in English or in Latin letters for a Hindi or Kannada task are refused by `check_draft` (`question_language`) and the model repeats the plan; a plan that finds nobody carries the note `nobody_found` (the synthetic workspace has no appointments, consents or last-week visits, so this is the right answer there).
