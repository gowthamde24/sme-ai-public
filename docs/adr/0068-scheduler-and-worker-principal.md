# ADR 0068: the scheduler (quiet-hours release, visit reminders, automatic no-show) and the worker's principal

Status: accepted for the local stage (job AW, 2026-10-11); amended by the owner's decision "approved = send" (job AY, see the addendum at the end). Builds on ADR 0013 (a non-human actor needs a dedicated principal, option B), ADR 0066 (the outbox and its policy) and ADR 0067 (store visits). Nothing is deployed; the only channel is the local fake.

## Context
Three things need something to happen **without a person at the keyboard**: a message held for the morning must go at 09:00 (quiet hours 21:00 to 09:00 India time), a customer with a confirmed visit should be reminded (the evening before, and a few hours before), and a visit nobody came to should not stay "confirmed" for ever. Until now the outbox dispatched only when an Owner or Admin submitted, approved or pressed "dispatch now".

The obstacle is **identity**. The API has no service-role key by design and acts only with a caller's own JWT (`Settings` docstring, ADR 0013); every outbox function checks `auth.uid()` and a workspace role. A background worker has no caller. ADR 0013 says a dedicated principal is required before the first scheduled or background actor. This ADR builds the smallest one.

## Decision
1. **One worker process, no queue, no new account, no new dependency.** `python -m app.scheduler.worker` (`make dev-worker-local`): every 60 seconds (`SCHEDULER_INTERVAL_SECONDS`, 5 to 3600) it runs one tick. A separate process, not a thread of the API: the API can be restarted without the schedule noticing, and the worker has no HTTP surface.
2. **The worker's identity is a principal the database knows.** An ordinary sign-in account that belongs to **no workspace** and that the **operator** registers in the database (`app.operator_register_scheduler(email)`, operator only: it refuses any session that carries a request identity, refuses an account that belongs to a workspace, and is executable by no client role). Its password is in the worker's environment only. Row-level security shows it nothing (it has no membership); its only power is EXECUTE on eleven `public.scheduler_*` SECURITY DEFINER functions, each of which starts with `app.is_scheduler()` and otherwise answers 42501. A trigger refuses to give the account a membership. Removing the registration (`app.operator_remove_scheduler`) takes the power away at once; the next call is refused.
   *Why not the alternatives:* a service-role key is standing authority over every table and breaks the project rule that the API has none; a direct Postgres login role would need a driver (a new dependency) and a database password in the worker's environment; running the worker with an Owner's JWT cannot work unattended (1-hour tokens, second factor) and would audit every automatic act as that person; `pg_cron` would run the SQL but the channel adapter lives in Python (a real WhatsApp adapter is an HTTP call); a per-workspace agent principal (ADR 0013 option B in full) is the right shape for a *model-driven* agent and is far more than a clock-driven worker needs.
3. **The two switches are enforced in the database, not in the worker's code.** The work functions answer "nothing" unless the **global outbox kill switch** AND the business's own **automatic sending** (`outbox_settings.auto_send_enabled`, default OFF) are on; `scheduler_tenants()` lists exactly those businesses (and `[]` while the global switch is off). A worker with a bug, or an attacker holding its password, still cannot touch a business that has not switched automatic sending on. The automatic no-show follows the same gate (the brief: the scheduler does nothing unless both are on) and has its own setting, default OFF.
4. **One code path to the channel.** The three outbox steps (`outbox_submit`, `outbox_claim_due`, `outbox_mark`) moved into cores (`app.outbox_submit_core`, `app.outbox_claim_due_core`, `app.outbox_mark_core`) that take no role decision. The old public functions keep their signature, grants, checks and answers (they are now wrappers: the same role check, then the core); the worker's `scheduler_*` functions call the same cores. So the send policy, the STOP / erasure / no-key / opt-in / daily-limit re-check at send time, quiet hours (a due message is pushed to the next 09:00), the lease and the idempotent mark are exactly a person's "dispatch now" and are never bypassed. In Python the worker uses the outbox's own `dispatch_due` loop (given a narrow `DispatchPort`). `test_migration_copies.py` pins that each core is the clock migration's body with exactly the role lines changed.
5. **Releasing.** `scheduler_claim_due` returns what is due (`scheduled_for` passed, not leased). Two workers never get the same message: the claim takes row locks with `FOR UPDATE SKIP LOCKED` and stamps `claimed_at`, a two-minute lease. A tick that dies after the channel took a message but before the database was told leaves it claimed; after the lease it is offered again **with the same message id**, which the real adapter must use as its idempotency key (ADR 0066 decision 6). This is at-least-once delivery, stated rather than hidden.
6. **Reminders.** `scheduler_due_reminders` lists what is due; `scheduler_queue_reminder` re-checks everything and queues one reminder through the outbox as `category visit`, `source system`, made by the scheduler principal, then the same tick releases it. Rules (all India time, by the database clock `app.outbox_now()`):
   * only for a **confirmed** visit that has not started (a booked-only visit, a cancelled one, a no-show: none);
   * **never in quiet hours** (nothing is queued at 21:00 to 08:59: it would only wait for the morning, which may be after the visit);
   * *evening before*: the visit is tomorrow, from the business's hour (default 18, allowed 9 to 20) until 21:00;
   * *heads-up*: from the business's minutes before (default 120, allowed 60 to 480), but never closer than 30 minutes;
   * not when a confirmation or reminder of the visit was made **after the window opened** (the customer was just told; also covers a reminder a person sent by hand);
   * **at most once per visit, kind and start time**: a record per reminder (`visit_reminders`, unique on visit, kind, start time) is written in the same transaction as the outbox message, under a per-visit advisory lock; every worker derives the same message id from the same inputs. A visit that **moves** is a new appointment (its start time differs) and is reminded again; the brief's "once per visit per type" is read as once per appointment time, because a reminder with the old time and none for the new one would send a customer to the wrong hour;
   * the words are the fixed templates of `app/visits/texts.py`, in the language the visit's **confirmation** went out in (English when there is none); a language no native reader has checked is submitted `uncertain`, so the outbox holds it for a person (`needs_approval / uncertain`). Money in the words is held by the policy like any message.
7. **Automatic no-show.** `scheduler_mark_no_shows`: a **confirmed** visit whose slot ended at least N minutes ago (default 30, allowed 5 to 720) becomes `no_show`, closed at the tick's instant, by the scheduler principal. Off by default (`no_show_enabled`); a visit the customer never confirmed (booked) is left for a person. Row locks with SKIP LOCKED.
8. **Settings** per business (`scheduler_settings`; Owner with a second factor writes, Owner and Admin read, `GET/PUT /v1/tenants/{id}/scheduler/settings`): the evening reminder on/off and hour, the heads-up on/off and minutes, the no-show on/off and minutes.
9. **Failure isolation.** A phase (reminders, release, no-show) that fails is counted and the others still run; a business that fails does not stop the others; a tick that fails (any exception) is logged by class name and the next one runs on its schedule (a slow tick does not push the schedule back; an overrunning one starts the next at once). A refused token (expired, or the account was removed) makes the worker sign in again before the next tick; a sign-in that fails is logged without a reason and retried. Only `KeyboardInterrupt` / SIGTERM stops it.
10. **Observability, counts only.** Each tick: one log line (`tenants sent failed reminders no_shows errors`, never a word, number, name, id or token); one **heartbeat** (`scheduler.heartbeat`, one row for the installation: last tick, interval, tick count, last error count); and, for each business with something to report, one row in `scheduler_runs` (sent, failed, reminders, no-shows, errors: integers only; an idle tick writes none, so the table does not grow by 1,440 rows a day per business). The **Owner's read** (`GET /v1/tenants/{id}/scheduler/status`, Owner and Admin): `platform_switch_on`, `auto_send_enabled`, `active` (both on), `worker_running` (a tick within three intervals), `last_run_at`, `next_run_at`, `interval_seconds`, `last_activity_at`, and today's (India day) counts. For a later web card.

## Consequences
* New: migration `20261109090000_aw_scheduler.sql` (private schema `scheduler` with `principals` and `heartbeat`; tables `scheduler_settings`, `visit_reminders`, `scheduler_runs`; the cores and wrappers; eleven public functions; two operator functions); API `app/scheduler/` (repository, sign-in session, tick, worker, models, routes); `make dev-worker-local`; pgTAP 79 (269 checks) and updates to 06, 12, 00001, 77; `services/ai-api/tests/test_scheduler_tick.py`, `test_scheduler_routes.py`, `tests/integration/test_scheduler_api.py`; runbook `docs/runbooks/scheduler-local.md`.
* A plain `TRUNCATE` of `store_visits` or `outbox_messages` is now refused by the foreign key from `visit_reminders` (0A000) before any guard trigger runs; tests use `TRUNCATE ... CASCADE`, which reaches the guards (all refuse, 42501).
* The worker's principal is **one account for every business** of an installation. That is standing authority over every business's queue, narrowed to the eleven functions and to businesses that switched automatic sending on, and recorded as the actor (`created_by`, `updated_by`). It is not option B in full (no per-business principal, no role enum, no change to core RLS). Before the first external customer the owner should decide whether this is enough or whether to issue one principal per business (the functions already take the business as an argument, so that is an authorisation change, not a rewrite). Listed in `docs/pre-pilot-checklist.md`.
* A message the Owner approved in a business that has automatic sending **off** is not released by the worker (the business is invisible to it); it waits for "dispatch now". This follows the brief literally; it can be relaxed later by letting the worker release owner-approved rows only.
* Delivery is at-least-once (decision 5). Nothing real exists to duplicate yet.
* The heartbeat is one row for the installation, not per business: a business sees whether the worker is alive, not that it looked at them specifically.
* `scheduler_runs`, `visit_reminders` and `scheduler_settings` hold no personal data (ids, kinds, times, integers); the erasure registry needs no entry. They are append-only (no update, delete or truncate); retention is not decided.
* The worker adds no dependency (httpx and the existing repository pattern).

## Addendum (job AY): approved = send

**Owner decision.** A message the Owner has approved is released by the worker **even when the business's automatic sending is off**, as long as the global switch is on. Approval is the Owner's consent to send. Automatic sending off still means nothing goes **without** an approval.

What changed (migration `20261110090100_ay_outbox_media.sql`; the cores and the three scheduler functions are replaced as full copies, pinned by `test_migration_copies_ay.py`):
* `scheduler_tenants()` lists a business that switched automatic sending on **or** has a queued message whose reason is `owner_approved`. While the global switch is off it is still `[]`.
* `scheduler_claim_due` asks the same core as before, with a new argument: `p_approved_only = not (automatic sending on)`. The core adds one line, `and (not p_approved_only or x.reason = 'owner_approved')`, so with automatic sending off the worker claims **only** approved messages. Everything else is unchanged and still applies at send time, in the same code a person's "dispatch now" runs: quiet hours (an approval at night is scheduled for the next 09:00 and released then, not at 08:59), STOP / withdrawn consent / erasure, the suppression key and opt-in, and the per-customer daily limit.
* A message that was **auto-allowed** earlier and is still queued when the business then switches automatic sending off is **not** released (nobody approved it); it waits for the Owner's "dispatch now". The people's `outbox_claim_due` is unchanged (`p_approved_only = false`).
* Reminders and the automatic no-show stay behind automatic sending (decision 3 stands for them). `scheduler_status` gains `releases_approved` (true while the global switch is on) beside `active` (both switches on), so the card can say "approved messages still go out".
* The Python side did not change: it asks the database which businesses to visit and hands each claim to the outbox's own dispatch loop.

Tests: pgTAP 80 section I pins 13:00, 22:00, 08:59 and 09:00 India time (day and night) and checks that approved messages go with automatic sending off, an auto-allowed one does not, STOP after approval blocks, the global switch off releases nothing, the status flag and the people's dispatch; `tests/integration/test_scheduler_api.py` runs it end to end with the real worker (approve at 22:00, nothing at 08:59, sent at 09:00). The consequence listed above ("Messages the Owner approved in a business with automatic sending OFF are not released by the worker") no longer holds and is struck from the pre-pilot checklist.
