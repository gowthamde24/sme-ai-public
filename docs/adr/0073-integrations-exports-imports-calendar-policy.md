# ADR 0073: files in and out: accounting export, spreadsheet import, visits calendar feed, policy acceptance

Status: accepted for the local stage (job BI, 2026-10-12). Builds on ADR 0010/0020 (lead import and suppression keys), ADR 0016 (a second factor for privileged actions), ADR 0021 (orders), ADR 0067 (store visits), ADR 0069 (the catalogue). Nothing is deployed.
Migrations `20261114090000` to `20261114090300`; pgTAP `83_bi_integrations`; runbooks `docs/runbooks/accounting-export.md` and `docs/runbooks/spreadsheet-import-and-calendar.md`.

## Decisions

1. **Accounting export is ONE database read plus pure writers.** `public.export_accounting_data` (Owner/Admin, second factor) returns the sales (accepted orders, dated by the India day of the `customer_accept` event) and payments (`record_payment`, `record_refund`) of an India-date window (at most 366 days, 2,000 sales, 5,000 payment events) and writes the audit event `export.create` (format, window, counts; no customer data) **in the same transaction**, so no export exists without a record. The API builds every file from one structure (`app/integrations/accounting.py`): Tally Prime XML (masters, vouchers, a README, in a zip), a Vyapar workbook, a plain CSV and a plain XLSX. Amounts come from integer paise; GST is split from the quote (CGST + SGST for an intra-state supply, IGST for inter-state, per rate), and any paisa difference between an order total and its parts goes to a `Round Off` line, so a voucher always balances. The party is the company name only: no contact person, phone or e-mail leaves.
2. **No GSTIN is stored today, so none is written** (the column exists and is empty). Adding one is a change to the erasure registry (a company-scope column) and is proposed as a separate job; it was kept out of this one because the erasure workflow is a hard gate.
3. **Vyapar.** The Vyapar app imports Parties and Items from an Excel template and has no documented sale-invoice import; invoices go through Vyapar TaxOne's Bulk Upload. The workbook therefore has four sheets (Parties, Items, Sales, Payments) and ONE table of header names (`app/integrations/vyapar.py: HEADERS`) because Vyapar publishes no header list: compare with the template the app gives you and rename if needed.
4. **Spreadsheet import never stores the file or its rows.** The upload is held in memory; a small job record (`integrations.import_jobs`) keeps the file's SHA-256, the mapping as column numbers, counts, and the first issues (line, closed code, field name). Preview → confirm: the confirm must carry the SAME file (hash) and needs a second factor; a finished job replays its result and imports nothing twice; a failed job may be run again. Customers go through the **existing lead import** (the same match keys, the same duplicate rule, the same real-data gate, batch id = job id): an existing customer is reported as a duplicate and **never changed**. A contact needs an e-mail address OR a phone number (job BO changed the lead import; before that an e-mail was required): a phone-only contact is imported, named after the shop when the sheet has no contact name (`contact_named_after_company`). Stock import only sets `stock_status` of catalogue items found by name (same match key); nothing is created or deleted. Headers are matched deterministically in English, Telugu, Hindi, Kannada and Tamil.
5. **Untrusted files.** CSV (UTF-8, UTF-16 with a BOM, tab or comma) and XLSX (first sheet; own reader on `zipfile` + `xml.etree`, no new dependency): limits on bytes, parts, rows, columns and cell length; an XML part with a DOCTYPE or ENTITY is refused; formula cells in XLSX are reported and their cached value is never used; text cells that look like formulas (and cells with hidden/bidirectional characters) refuse their row with a closed code; no issue ever echoes a cell value.
6. **The calendar feed is a capability URL.** A member's feed address holds a 256-bit token; only its SHA-256 is stored; one active token per member and business (rotating revokes the old); the token is shown once. `public.calendar_feed_read(hash)` is **the one function `anon` may execute** (pgTAP 06 names it; a calendar app has no sign-in); it returns only when, how long, the state, the party size and "first name + last initial" ("Customer" for an erased person), for tokens that are active and whose member still belongs to the business. The API adds in-memory rate limits (per token, per address, and a stricter one for unknown tokens) and answers one 404 for unknown, revoked and malformed tokens.
7. **Policy acceptance.** `integrations.policy_acceptances` (user, kind, version, time, how). The API publishes the current versions (settings `TERMS_VERSION`, `PRIVACY_VERSION`) at `GET /v1/policies/current` and refuses to record any other. `POST /v1/account/setup` accepts the two versions and records them first; `POST /v1/me/policy-acceptances` records a later acceptance.
8. **Voice status** (`GET /assistant/voice/status`) says what is switched on without calling any provider.

## Consequences and risks
* The Tally files follow Tally's published examples but were not imported into a real Tally here (none is available): the runbook says to try one voucher on a backup company first. Tax ledgers are plain "Duties & Taxes" ledgers without GST type or rate; vouchers are accounting vouchers (no stock items, no HSN).
* Re-importing the same Tally file creates the vouchers again (no GUID in the file); the runbook says so.
* The Vyapar header names are not official (see 3).
* The feed's rate limits live in one process's memory, like the sign-up limiter.
* `anon` can now execute one function; the token's strength is the protection, and the function reveals nothing for a wrong token.
* Phone-only customers lose their contact on import until the lead import accepts a contact without an e-mail (proposed follow-up).
