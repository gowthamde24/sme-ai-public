# ADR 0081: GSTIN (the shop's and the customers'): validation, storage, erasure, display and the accounting files

Status: accepted for the local stage (job CA, 2026-10-12). Builds on ADR 0014 (erasure and its registry), ADR 0021 (orders), ADR 0073 (the accounting export, which said "no GSTIN is stored yet"), ADR 0078 (no public API verifies a GSTIN).
Migration `20261121090000_ca_gstin.sql`; pgTAP `91_ca_gstin` (63 checks); tests `test_ca_gstin.py` (unit and integration), `test_migration_copies_ca.py`; runbook `docs/runbooks/gstin.md`.

## Decisions
1. **Validate offline, in two places that are proved equal.** A GSTIN is 15 characters: a state code (01 to 38, 97, 99), the holder's PAN shape, an entity number, the letter `Z`, and a check character (Luhn mod 36 over the first 14). `app.gstin_is_valid` (SQL, immutable, used by the tables' CHECKs) and `app/gstin.py` (Python, used by the API models for a plain 422) implement the same rule; an integration test compares them on more than 1,500 numbers (valid, perturbed, random) and a pgTAP file pins the published examples (`27AAPFU0939F1ZV`, `29AAGCB7383J1Z4`, `24AAACC1206D1ZM`, which also fixed the algorithm: two numbers I remembered from other sources failed the check and were not used). Well formed is all it says. There is no public API to verify existence or activity (the GST portal's search is behind a captcha, ADR 0078), so no verification is built.
2. **A customer's GSTIN is a column of `companies`** (nullable, `CHECK` valid and clean). It holds the proprietor's PAN, so it is **PII**: classified `PII:`, on the company audit trigger's PII list (the audit log records that the field changed, never the value), a row in `erasure.registry` for the company scope (nulled) and the sweep. `app.erase_company` names its columns one by one (and had been re-copied by five migrations), so it was replaced once more as a FULL COPY of job BB's plus one line, pinned by `test_migration_copies_ca.py` (BB's pin now accepts CA as the later copy). The generic erasure test planter plants a GSTIN so the canary tests cover the column. The column grants (insert, update) were added for the signed-in role; `app.gstin_is_valid` is executable by it because a CHECK runs with the writer's rights.
3. **The shop's own GSTIN is `public.business_profile`** (one row per business, no client write grant, written only by `public.business_profile_set`, Owner or Admin with a second factor; read by every member by row-level security). It is a business identifier the shop prints on its invoices, classified SAFE and audited by value. The route `PUT /business-profile` requires the `gstin` key (an empty body must not clear it) and accepts null to clear.
4. **Shown, not copied.** An order's detail and a quote's detail carry `customer_gstin` (the company of the lead) and `shop_gstin`, read with the caller's token when the document is shown; the quote list row carries `customer_gstin`. Nothing is written onto the quote or the order: the quote's customer text and canonical hash are fixed by the pinned engine (non-negotiable 4, ADR 0019) and a corrected number should show at once. On a quote the fields are left out of the JSON when empty, which keeps the golden "a list-price quote reads exactly as before". A failed read is a missing value, never a failed screen.
5. **The accounting export** (`public.export_accounting_data`, replaced as a FULL COPY of job BI's, pinned) returns each order's and payment's customer GSTIN (null for an erased customer) and the shop's. The CSV and XLSX fill the existing `GSTIN` column and add `Seller GSTIN` as the last column; the Vyapar workbook fills Parties and Sales GSTIN; **the Tally files are unchanged**: the XML tag names for a ledger's registration details could not be verified, and a wrong tag makes Tally refuse the file. A number the application would refuse never reaches a file (the parser re-checks).
6. **Not done:** verification against the GST portal or a provider; a GSTIN column in the spreadsheet import; the company's GSTIN as an identifier of the erasure sweep (a GSTIN typed into a free-text note is not found: noted in the pre-pilot checklist); the GSTIN in the quote's customer text.

## What the work found
* The registry guards made the missing pieces fail loudly (a column grant, the PII audit list, the tenant-table role matrix, the policy shape) and the first pgTAP run on the company-scope erasure showed that a registry row alone does nothing: the function lists its columns. The test now plants a GSTIN and proves the erasure nulls it.

## Consequences and risks
* The number is stored as the owner or a customer's clerk typed it, after the form check; an old or wrong-but-well-formed number is possible (existence is not checked).
* Special registrations (government and UN bodies, whose 14th character is not `Z`) are refused.
* The state of a GSTIN is the GST portal's state code list as known on 2026-10-12 (code 28 is the old Andhra Pradesh, kept valid for existing numbers).
* Web: `customer_gstin` and `shop_gstin` are new optional fields on orders and quotes; `CompanyOut.gstin` is a new required-nullable field (contracts regenerated).
