# ADR 0070: outbox gaps (gloss, events, filtered log), photos for a real channel, per-business quiet hours, a lighter Agent OWL

Status: accepted for the local stage (job BB, 2026-10-11). Builds on ADR 0066 (the outbox), 0068 (the scheduler's principal) and 0069 (the catalogue). Nothing is deployed; the only channel is the local fake.

## Context
The Outbox page (job AX) listed what it could not draw: the English gloss of a message in another language, the steps of a message, a log that can be filtered and paged on the server, and counts for its tabs. A real WhatsApp adapter will later need the photos of a message as addresses it can fetch. The owner wants quiet hours that fit the business. And every Agent OWL request carried the definitions of every tool, about two thirds of the request, which a free model tier pays for on every question.

## Decisions
1. **Gloss.** `outbox_messages.gloss_en` (2 to 3,000 characters, clean text, nullable). Set when the message is made (`gloss_en` on submit) or edited (`gloss_en` on edit; editing the words without a gloss clears it, because the old one would describe other words). It is personal data like the words: the audit trigger lists it, the erasure registry has its four scopes, `erase_contact` / `erase_company` erase it, the guard lets it change only while the message waits for approval, and it is part of the request hash (a retry with another gloss is a conflict, 23505).
2. **Events.** `outbox_events` is append-only (no update, delete or truncate), one row per step: made, queued, held, needs_approval, approved, rejected, edited, blocked, sent, failed, with a closed `reason` word, the time (the outbox clock), and the actor kind (person, assistant, worker, system) with the user id only for a person or Agent OWL acting for one. **No text, phone number or name is in an event.** ONE trigger on the message row writes them, so every path (a person, the assistant, the worker, STOP) is covered and none can forget; it stays quiet while an erasure runs (a tombstone is not an edit). The API shows them in the detail only (`events`, null in lists), with display names read from `users` for the people the caller shares a business with.
3. **The log.** `outbox_list` (a page of ids for a tab, a customer, an India-date range, keyset by `(created_at, id)`) and `outbox_summary` (counts per tab plus `due_now` / `held_for_later`), both Owner / Admin / Sales proven inside the definer function. The customer filter matches the company's and the contact's NAME, never the words of a message; `%` and `_` are literal. `GET /outbox/messages` takes `tab`, `customer`, `from`, `to` (not combined with `status` / `lead_id`: 422), `GET /outbox/summary` the same filters. `POST /outbox/dispatch` was already per business (the tenant is in the path); it now also says `still_due`, `held_for_later`, `platform_switch_on` and `retry_later`.
4. **Photos for a real channel.** A message the worker has CLAIMED (status queued, lease younger than ten minutes) lets the registered worker principal, and nobody else, read exactly the files of that message's photos (`app.worker_may_read_object`, one more storage rule). The worker signs addresses with its own token (`StorageClient.sign(..., expires=300)`), and `dispatch_due` hands the adapter `MediaRef.url`. If an address cannot be made for any photo the message is neither sent nor marked: its lease lapses and the next round offers it again (`retry_later`, counted as a tick error). A person's Dispatch does the same with their own token. No service-role key exists anywhere. **The message id is the adapter's idempotency key** (`OutgoingMessage.idempotency_key`; `media_key(n)` = `"<id>:<n>"` for photo n), because delivery is at-least-once (ADR 0068, decision 5).
5. **Quiet hours per business.** `outbox_settings.quiet_start_hour` (19 to 23, default 21) and `quiet_end_hour` (7 to 10, default 9). `app.outbox_quiet_hours_of(tenant)` is the one place they are read; the five places that decide (the send policy, the Owner's approval, the release of a due message, the two reminder checks) pass the business to `outbox_in_quiet_hours(at, tenant)` / `outbox_next_open(at, tenant)` (full copies, pinned by `test_migration_copies_bb.py`). `PUT /outbox/settings` takes optional `quiet_hours_start` / `quiet_hours_end` (Owner with a second factor; a field left out keeps its value). Interaction to know: a reminder is never queued in quiet hours, so a start of 19:00 with the evening reminder at 20:00 gives no evening reminder (the heads-up still goes). A message already scheduled for the old morning keeps that time until it is claimed; the claim re-checks against the hours in force then.
6. **A lighter Agent OWL.** `app/assistant/router.py` decides, once per question and with no model call, which tools to describe: the core tools always; the two catalogue tools only for photos, pictures, the catalogue, designs, colours, fabrics, stock, or sarees / fabrics / colours with a verb of showing or sending; the visit tool only for visits, appointments, slots, bookings. Five languages (English, Telugu, Hindi, Kannada, Tamil), plain lists, tested one by one; the last four lines of the chat carry a follow-up over. The system prompt mentions the photos tool only when it is offered. The runner refuses a call to a tool that was not offered exactly like an unknown tool. Measured (estimated tokens a question): core 2,982 to 3,263 (was 3,705 to 3,986), catalogue 3,679 to 3,693, visits 3,277, both 3,855; ceilings are per path in `test_assistant_tokens.py`.

## Consequences
* New migrations `20261111090000_bb_outbox_gloss_events_list.sql` and `20261111090100_bb_quiet_hours.sql`; pgTAP 81; `test_migration_copies_bb.py`; unit tests (`test_outbox_routes.py`, `test_assistant_router.py`, `test_scheduler_tick.py`); integration `test_bb_outbox_api.py` and an end-to-end worker photo test in `test_scheduler_api.py`.
* The worker's principal can now read the files of claimed messages in ANY business (it is one principal for the installation, ADR 0068); it still reads nothing of a message that is not claimed. The per-business principal decision in the pre-pilot checklist stands.
* The router is a floor, not a promise: a question phrased without a trigger word does not get the catalogue tools and the model is told, by refusal, that it cannot. The lists are data; adding a word is a one-line change with a test. Existing integration tests that scripted a catalogue call under a question like "send it" now use questions that really name photos.
* Events are written inside the same transaction as the change; they cannot disagree with the message.
