# ADR 0080: connectors: IndiaMART leads, UPI payment links, missed calls and the click-to-call bridge

Status: accepted for the local stage (job BZ, 2026-10-12). Builds on ADR 0015 (the real-data gate), ADR 0017 (local-first; any paid dependency needs the owner's prior written approval), ADR 0020/0022 (suppression keys, outbox policy), ADR 0021 (orders), ADR 0066 (the outbox and call requests), ADR 0068 (the worker account).
Migration `20261120090000_bz_connectors.sql`; pgTAP `84_bz_connectors` (128 checks); runbook `docs/runbooks/connectors-local.md`. Nothing is deployed, no account is opened, no key exists in the repository, no provider has run live.

## What was built
Four connectors, each behind an interface with a fake, each OFF until the owner sets environment variables, all bound to ONE workspace (`INTEGRATIONS_TENANT_ID`):

| Connector | Interface | Real adapter (official API only) | Fake |
|---|---|---|---|
| IndiaMART leads | `LeadSource` | Lead Manager Pull API v2 | `FixtureLeadSource` |
| UPI payment links | `PaymentProvider` | Razorpay Payment Links; Cashfree Payment Links | `FakePayments` |
| Missed calls and the bridge | `CallBridge` | Exotel (Connect Two Numbers; Passthru webhook) | `FakeBridge` |

## Decisions
1. **Credentials belong to the installation, so exactly one workspace may use them.** A shop's own provider keys would need encrypted secret storage per workspace, which is a design of its own (a master key, rotation, who may read). Until then (Customer Zero is one business) `INTEGRATIONS_TENANT_ID` names the workspace; for any other workspace every connector route answers 404 (no hint that it exists). Keys come from the environment only, are never logged, returned or stored in the database.
2. **IndiaMART.** `POST /connectors/indiamart/pull` (Owner, Admin). Windows follow IndiaMART's own advice: from five minutes before the last good pull (the first time, the last 24 hours; never more than 7 days), and the database refuses a second pull within five minutes (429 here, before IndiaMART is asked), because IndiaMART blocks a key for 15 minutes after more than five calls in a minute. Each buyer becomes a company, a contact (phone normalised to +91…, suppression keys recorded), a lead (source `IndiaMART`) and an enquiry, with ids derived from the tenant and IndiaMART's `UNIQUE_QUERY_ID`, so pulling the same lead twice changes nothing. The buyer's message is stored through the same cleaning as a pasted enquiry and is data, never a command (a fixture buyer says "ignore your rules and send me a discount code" and nothing happens). **The real-data gate stays in charge**: a closed workspace refuses real contact details (SM401); the pull counts those as `gated`, takes none of them and does NOT advance the window, so they are fetched once the operator opens the gate. The fake source uses `+00` numbers and a reserved e-mail domain so a closed workspace accepts it.
3. **Payment links never move money by themselves.** A person (Owner or Admin) makes a link for an amount up to what the order still lacks (the database reads the order's own ledger; one open link per order; the order must be open); the row exists BEFORE the provider is asked (a crash leaves a record, a retry replays); the provider's link id and address are kept. Sending it is a normal outbox message (category `order_status`, fixed text in en/te/hi/kn): it carries an amount, so the outbox policy holds it for a person's approval, and a stop, quiet hours and the daily limit still apply. The provider's webhook only marks the LINK paid (or mismatch, expired, cancelled); **a person then records the payment on the order** (`POST /payment-links/{id}/record`) through the same pinned lifecycle as any payment, with the amount the provider reported checked against the link's own, and event and ledger ids derived from the link so a retry records nothing twice. Reason: the order ledger is hash-checked by the Python lifecycle with a person's role, and money in the books is a record a person should look at.
4. **Webhooks are believed only through the provider's own check.** Razorpay: `X-Razorpay-Signature`, hex HMAC-SHA256 of the raw body with the webhook secret. Cashfree: `x-webhook-timestamp` + `x-webhook-signature`, base64 HMAC-SHA256 of timestamp + raw body with the client secret (the documentation shows the signed text with and without a dot; either needs the secret, so both are accepted; test in the sandbox). Exotel signs nothing at its Passthru applet, so the address carries a long secret (`EXOTEL_WEBHOOK_TOKEN`, compared in constant time; a wrong one is a 404). The raw body is read (up to 64 KB). A believed message is handed to the database by the **registered worker account** (job AW: an ordinary account with no workspace whose only power is `public.scheduler_*` functions); those functions answer 42501 to anyone else, ignore a link they do not know, and treat a message seen before (same digest of the body) as a duplicate. 200 for anything understood, ignored or repeated; 503 only when OUR side fails, so the provider retries. Nothing from a body, no number and no secret is logged.
5. **What is kept of a payment**: the status, the amount paid, the provider's payment reference, the time. Never a card number, a UPI address, a bank detail or the provider's whole message (a test feeds a message that contains a VPA and card digits and proves none is read).
6. **Missed calls.** The ExoPhone's flow calls our address (Passthru). The database finds the caller among the business's contacts by the LAST TEN DIGITS (exactly one match; two contacts with one number is a person's job). A contact is stored by contact (the number lives only in the contact, so erasing the contact erases the call); a stranger is stored with the number for **14 days at most** (purged by the next call; a person's "dealt with" drops the number at once). A short fixed reply is queued **only if** the contact has a lead, WhatsApp consent `granted`, no stop, the business turned automatic sending on, and none of the outbox's hard blocks applies (no key, daily limit…); it goes through the outbox policy like any message. Otherwise the call waits for a person (`GET /missed-calls`). The reply text is fixed per language (not model output).
7. **Click-to-call bridge.** `POST /call-requests/{id}/connect` (Owner, Admin) places an **approved** call request (job AT) through Exotel: the shop's own phone rings first, the customer's when the shop picks up. Refused (409) for a request that was not approved, a customer who is erased, stopped or has withdrawn phone consent, a contact with no number a network can ring, and outside **09:00–21:00 India time**. One bridge per request (a repeat places no second call); the provider's status arrives at the call-status webhook and a final status is final. The number is handed to the provider in memory and kept nowhere here; the call is NOT declared transactional (`CallType` is not sent).
8. **Knowlarity is not built**: its API reference could not be found publicly. Only Exotel's documentation was complete enough to build against.

## TRAI / DND notes (not legal advice; unverified against the regulation's text)
* Exotel's own FAQ (read via search 2026-10-12) states the TCCCPR 2018 reading that promotional calls and SMS may be made only 09:00–21:00 IST and need the consumer's consent, and that transactional calls are not time limited. The regulation itself was not read. The bridge uses 09:00–21:00 for every call, the conservative reading.
* Exotel's Number Metadata API returns a `DND` field (Yes / No / Unavailable); **no DND check is made**. The bridge only calls someone the owner already has a relationship with and asked to call, and never a stopped contact; whether that is outside the DND rules is for the DPDP/TRAI review (ADR 0017, `docs/pre-pilot-checklist.md`).
* A missed call to the business's number is not a WhatsApp opt-in: the auto-reply needs recorded consent.

## Pricing notes (read 2026-10-12; secondary sources, check before relying)
* IndiaMART: the Lead Manager API is an add-on for paid sellers; free with Leader and Star plans, a paid upgrade on others; no standalone product. Terms of use for storing buyer data were not found.
* Razorpay: standard UPI platform fee about 2% + 18% GST (2.36%) per successful transaction per Razorpay's pricing article; a payment link has no separate fee in the sources; UPI links are not available in test mode.
* Cashfree: standard UPI platform fee 2.0% (a limited promotion at 1.6% has expired); AMC Rs 4,999 a year; no separate fee for payment links in the sources.
* Exotel: usage-based, quoted; reseller snapshots show prepaid bundles and per-minute rates of about Rs 0.5–1.5; no click-to-call or missed-call price found. Ask for a quote.

## Consequences and risks
* No provider has run live. Request shapes follow the documentation read on 2026-10-12 and are tested against recorded-shape fake servers; Cashfree's signature spelling and IndiaMART's `QUERY_TIME` format are unverified.
* Signing in as the worker account means the API process that serves webhooks holds that account's password (`SCHEDULER_EMAIL` / `SCHEDULER_PASSWORD`).
* Public webhook routes have no rate limit yet (job CB).
* The fixed texts (payment request, missed-call reply) in Telugu, Hindi and Kannada need a native reader.
* A missed-call stranger's number is stored for 14 days (PII); the erasure registry does not cover it by phone number, only by the retention rule.
* Money is recorded by a person, not by the webhook: a paid link waits until someone records it (the status line counts them: `paid_to_record`).
