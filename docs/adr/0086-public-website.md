# ADR 0086: the public website (job CM)

Status: **ACCEPTED** by the owner's direction of 2026-10-14 (the Stack19 blueprint, sections 0, 1, 7, 8, 9, 12 and 13; job CM, wave 2). The web lane only: **no backend, database or API change.**

## Decision

1. **One set of server-rendered pages in four languages, with the language in the address.** English is unprefixed, `/te`, `/hi`, `/kn` are prefixes. Two route files (`app/[first]`, `app/[first]/[second]`) hand the segments to `resolveSite` (`lib/site/routes.ts`), which answers a language and a page or a 404. The words are `i18n/strings/site.json` (221 keys; Telugu, Hindi and Kannada are machine-written drafts, marked, and the page says so). The old landing words and components were deleted; the banned-word and forbidden-claim rules of the old landing apply to the new words (no guarantee, no percentage, no count of customers, nothing about where data is kept that is not true today).
2. **A business type's page comes from the pack files, in a file of its own.** Landing content lives in `packages/packs/<id>/landing.json` (schema `landing.schema.json`, checked by `scripts/packs_check.py`), **not** in `pack.json`, because `pack.json` is hash-synced into database migrations (a change to it needs a version bump and a migration, for words only a web page reads). The schema is closed (the owl list, the icon list, three optional blocks that are present exactly when the pack has the module: `calculator` needs `quotes`, `fee_preview` needs `fees`, `children_promise`), every text is `{en, te, hi, kn}` with only `{brand}` as a placeholder, and no price or percentage may appear in a text. A generator (`apps/web/scripts/site-packs.mjs`, `make site-packs`) joins `pack.json` and `landing.json` into one committed bundle the pages read; a test and `make packs-check` fail when it is stale. No business type is named in the web's code: a new `landing.json` is a new page, card, sitemap entry and share picture with no code. The page's address is the landing's `slug`, not the pack's id.
3. **Prices in one file, words without numbers.** `lib/site/plans.ts` holds the trial length, the three plans, done-for-you and the rupee format; the texts have placeholders for them. Billing is off and the page says so. The pricing decision document was not available to this job: the founding offer reads "details on WhatsApp", plan limits are "being set", fair use is a meter with no number. The owner fills these in later in one file and a few strings.
4. **Lead capture without a backend: a prefilled WhatsApp chat to our own number, nothing stored.** The contact form and the calculator call a server action that checks consent and a clean name, counts the try against a per-address hourly limit (the sign-up limiter, `SITE_LEAD_MAX_PER_HOUR`, default 10), works the calculator out again on the server (the browser's numbers are never trusted) and returns a `wa.me` address of `STACK19_WHATSAPP` (server-only configuration) with the message filled in. The visitor presses send in their own WhatsApp. No visitor data is stored or sent anywhere by us; the calculator's "lands as an enquiry only when a business has opted in" needs a public lead API, a table and a consent record, which is a later backend job. When the number is not set the pages say chat is not set up and show no button.
5. **The calculator is the quote engine's, not a copy.** `lib/site/paver.ts` imports `calculate` and `formatRupees` from `packages/quote-engine/ts/construction.ts` through a path alias (`@quote-engine/construction`); the Docker web image copies that folder. Same inputs run in the browser (live result) and on the server (the message). No money rule is written in the web; a price is only the visitor's own and the amount shown is before GST and transport.
6. **Search and sharing.** Per-language canonical and hreflang alternates, a share picture for the home page and for each business type page (1200 x 630, the plush owl, the type's accent colour; `npm run og:images`), `FAQPage` and `SoftwareApplication` schema.org data, a sitemap of every page in every language. All of it stays `noindex` and empty until the launch switch (`NEXT_PUBLIC_SITE_LIVE`), the owner's decision of 2026-10-07. The JSON-LD script is the one place the web writes raw HTML (`dangerouslySetInnerHTML` with `<` escaped); the guard test allows exactly that file.
7. **Small on a slow phone.** Pages are server components; only the header menu's language and theme controls, the calculator and the contact form are client code, and none of them imports the dictionary or the pack bundle (a test keeps four languages of every page out of the browser). The plush owl is a webp with a 128 and 256 px `srcset`; the one above the fold loads eagerly with high priority, the others lazily.

## Consequences and what is not decided here

* No public lead API, table or consent record exists; until it does the lead is a WhatsApp message in Stack19's own number. A business-side "opt in to receive website enquiries" is a later job.
* The help index lists seven topics and has no separate articles. Hosting is described honestly ("not hosted for real customers yet"); no region or certification claim is made.
* Telugu, Hindi and Kannada words need a native reviewer before launch (the banner stays until then).
* The repository copy of the blueprint (`docs/plans/stack19-blueprint.md`) lacks section 13 and the founding-offer terms; the Desktop copy is the current one.
