# ADR 0077: the team, the shop's basics, the weekly report, notifications and web-push

Status: accepted for the local stage (job BY, 2026-10-12). Branch `api/by-web-apis`, built on `origin/main`. Migrations `20261118090000_by_team_invitations.sql`, `20261118090100_by_workspace_report.sql`, `20261118090200_by_notifications_push.sql`; pgTAP `87_by_team`, `88_by_profile_report`, `89_by_notifications`. Nothing is deployed; push is off until the owner sets VAPID keys.

## 1. The team (members and invitations)
`docs/plans/members-and-invitations.md` (the owner's decisions of 2026-10-06) is built as designed:
* A person joins by a **one-time code** that the Owner or an Admin makes (second factor) and hands over by any channel: in person, on paper, WhatsApp, e-mail. 20 Crockford base32 symbols (100 bits) in four groups; only the SHA-256 of the **normalised** code is stored (case folded, spaces and hyphens removed, O to 0, I and L to 1, U refused); the code is returned **once** (an exact retry returns the same invitation without it: lose it, revoke and make another). 7 days by default, at most 30; at most 20 pending per workspace; an optional label of up to 60 characters that cannot hold a run of seven digits or an at sign (it is cleared when the workspace is erased).
* **No Owner invitation, ever**: role `owner` is refused for everyone, the table's check refuses it too; an Admin invites Sales and Viewers only. An Owner is added by the operator (`app.operator_add_owner_exception`, now capped at three Owners, a full copy pinned by `test_migration_copies_by`).
* `accept_invitation(code)` **never raises on a wrong code**: a raise would roll back the failed-attempt row and the lock would never count. Unknown, expired, used, revoked and other-workspace codes take one path and give one answer (`invalid`); five failures in an hour lock the caller (`locked`, the code is not even looked at); old attempts are purged after 24 hours. Only after the code is PROVEN valid are the specific refusals told: a second factor for an Admin invitation (SM306, no failure recorded), already a member (SM247, so it is never an oracle for who belongs). The API maps the two results to `400 invitation_invalid` and `429 invitation_locked`, and adds a coarser per-address limit. The integration test shows the attempt rows survive across requests and two or four people presenting one code at once make exactly one member.
* Role changes and removals: closed reasons (`left`, `role_changed`, `no_longer_works_here`, `access_no_longer_needed`, `security_concern`, `other`), no free text; nobody changes their own role; an Admin changes Sales and Viewer only; an Owner is never changed or removed from the app; the only Owner cannot leave (SM244). **Removal** ends access at once (every policy reads `memberships`), unassigns the person's leads and opportunities, cancels their running agent runs, revokes their pending invitations, and answers with **counts only**; an Admin who made invitations has them revoked.
* New SQLSTATEs SM242 to SM248 (SM240 and SM241 are results, not errors); the audit events (`invitation.created|accepted|revoked`, `member.role_changed`, `member.removed`) carry roles, reasons and counts, never a code or a label.
* **Not done: the client write grants of `memberships` are NOT revoked yet** (plan decision 12). Every integration fixture (`crm_support.World` and about a dozen suites), the MFA tests, the last-owner race test and the rehearsal driver still add members by a direct write; revoking now would break them all. Until the follow-up (move the fixtures to invitations, then `revoke insert, update, delete on public.memberships from authenticated`), an Owner with a second factor can still add any existing account in a single write. This is stated in the report as the main open point of the team.

## 2. The shop's basics
`workspace.profiles` (town, languages from en/te/hi/kn/ta) and `workspace_profile_get/save`: the shop NAME is the workspace's name (saving renames it); each field optional; the answer says `setup_complete` and what is `missing` for the setup wizard. Owner and Admin save (no second factor: it is not a risky setting).

## 3. The weekly report
One call, `weekly_report(tenant, week_start?)`, for Owner and Admin, the **India week (Monday to Sunday)**, any of the last 104 weeks:
* **visits** scheduled for that week (by their own India date): booked (not cancelled), arrived, bought, will return, not interested, no-show, cancelled;
* **messages**: sent in the week (by `sent_at`), and made in the week and now failed / still waiting / blocked;
* **response**: for every customer WhatsApp message that is the FIRST since our last message, the time to our next sent message; the median in seconds, how many were asked, answered, unanswered (wall-clock time, not business hours);
* **top sarees**: the five catalogue items whose photos went out most in sent messages that week;
* **AI allowance used** (percent) for the current week only (the allowance's own week, which is UTC-based; a past week has none).
Checked at the edges of the India week (Monday 00:00 in, Sunday 23:30 in, Monday 00:30 out) and for isolation.

## 4. Notifications and web-push
* **The feed.** `app.needs_you_items(tenant, user)` is the same five kinds, with the same role rules, as `today_summary`; a pgTAP test pins them equal per role. Unread is per member: a watermark (`notify.member_state.last_seen_at`); an item is unread when it is newer. `POST .../notifications/seen` moves the watermark. A Sales member or Viewer has an empty feed (they decide nothing).
* **Web-push**, on RFC 8291 (`aes128gcm`) and RFC 8292 (VAPID), written with the `cryptography` library that PyJWT already requires: **no new dependency**. The implementation reproduces **RFC 8291's own worked example byte for byte** (a unit test) and round-trips through an independently written decryptor. Subscriptions (endpoint and keys: secrets) live in the private `notify` schema and leave the database only to the worker. **Off by default**: a member opts in per workspace; switching on counts what already waits as told, so only things that arrive AFTER are pushed. The worker (the scheduler account) asks the database for each opted-in member's new items, sends **one** notification per member and pass, reports each subscription's answer (404 or 410 deletes it, five failures in a row delete it), and marks the items told once at least one browser accepted. Pushes are held during the business's quiet hours (21:00 to 09:00 by default; the outbox's own rule and clock seam). **The text is a fixed sentence by kind plus a count, never a customer's name or an amount** (the payload also carries the kinds so the browser can localize).
* VAPID keys come only from the environment, entered hidden: `VAPID_PRIVATE_KEY` (32 bytes in URL-safe base64, or a PEM), `VAPID_SUBJECT` (`mailto:` or `https:`), optionally `VAPID_PUBLIC_KEY` (checked to match). Without both, subscriptions and the feed work and nothing is pushed.

## Consequences and risks
* Real push services (Google, Apple, Mozilla) were not contacted. The format is the RFC's and its example passes; a real browser is the final proof (runbook: how to try).
* A push for an item can be repeated only if the database is unreachable between the send and the mark.
* The invitation code is a bearer secret until used: show it once, advise handing it over privately; a code typed wrongly five times locks that person for an hour.
* Pending: revoking the direct membership grants; e-mail delivery of invitations (needs SMTP and the approval path: the plan's section 3.5); the shop-name change is not shown to other members' sessions until they reload.
