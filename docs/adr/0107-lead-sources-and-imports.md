# ADR 0107: Lead sources and imports: files, sheets, pasted lists, vCards and live sources, one pipeline (job DR / A2)

Status: built on branch `api/dr-lead-sources` (night run 27 Oct 2026), stacked on `api/dr-leads-pack` (A1, #119). Source: night4-c1.md part A2. The contract is `docs/contracts/lead-sources.md`.

## Decision
1. **One pipeline for every arrival** (`app.lead_intake_core`, migration `20261205090000_dr_lead_sources.sql`): a bulk import, a website form, a portal's mail, Meta, IndiaMART and a kept-in-sync Google Sheet all end in the same database function. The API reads and cleans text and computes the suppression keys; the database de-duplicates, flags, records consent and writes. Work per row is atomic (a savepoint): a refused row never stops the others, and a preview is the same function rolled back, so its counts cannot disagree with the import.
2. **De-duplication by phone** (`app.phone_norm`, the comparison form used everywhere: `+91`, `0` and spaces ignored), then by e-mail. A repeat is not a second lead: it becomes a `repeat` arrival on the person's newest live lead (`public.lead_arrivals`: what they wrote, from which source, when), so the history of "this person asked again from another portal" is kept. The same phone twice in one file is dropped before the database (the first row wins).
3. **A lead of a person with no company** uses the placeholder company that `app.contact_lead` already makes for guardians and missed callers (a lead with a contact needs a company).
4. **Invalid numbers** (not an Indian mobile, not another country's 8 to 15 digits, not the reserved `+00` synthetic form) are not imported unless the row has an e-mail address; then the person is stored without a number and flagged `invalid_number`. **Do-Not-Disturb** comes from a lookup interface (`DndLookup`; only a fake exists: no provider is chosen): a marked number keeps WhatsApp and loses the `phone` consent (no promotional call), and the flag `dnd` is shown.
5. **Consent is explicit and the owner's.** Only an Owner or an Admin can confirm it (a Sales member imports without it: nothing is sent to those leads). A bulk import stores the owner's confirmation once (`public.lead_consents`: who, when, which list, purpose, basis, how collected, wording version; append-only) and every contact it creates gets WhatsApp, phone (unless DND) and e-mail consent recorded against it (`consent_events.evidence_ref = lcn:<id>`). Without a confirmation the leads are stored with consent "unknown": the outbox sends them nothing. A withdrawal is never undone by an import, and a suppressed person is skipped.
6. **Opt-outs are respected before anything is stored.** The API computes the suppression keys (the key never reaches the database) and sends them with each row; a row whose identifier is on the opt-out list is `blocked` (`opted_out`) and nothing of it is stored; otherwise the keys are recorded on the contact so a later opt-out finds them.
7. **The real-data gate is respected** by the existing contact trigger: with the gate closed a real number or address is refused row by row (`real_data_gate`), the invented ones are accepted.
8. **Column matching: rules first, the model last, the owner always.** Headers in English, Telugu, Hindi, Kannada, Tamil and Malayalam (and messy ones) are scored against synonyms; an unnamed column is placed by the shape of its values (ten digits, an @). Only columns the rules cannot place go to the model, as a run of the assistant (limits, cost reserved and recorded): it sees the header (untrusted, delimited) and a SHAPE of the values ("10 digits", "short text"), **never a value**; its answer is checked by code (a free known field, a real column, each field once) and is only a suggestion. A pasted list and a vCard need no mapping.
9. **Google Sheets without a Google key:** the sheet must be readable without signing in ("Anyone with the link can view" or "Publish to the web"); only `docs.google.com` is contacted, over https, redirects only to Google hosts, an HTML answer is a sign-in page (`sheet_not_public`). The same strict file reader is used. "Keep syncing" is a link row the worker pulls every 15 minutes (the database says which are due); rows seen are skipped (the phone is the identity); a changed header row stops the link (`columns_changed`) instead of guessing. A **service account** for private sheets is a documented gap (see Needs owner): the access endpoint says `available:false`.
10. **Public doors without a service key.** There is none in this API, so the public routes (`/v1/lead-intake/...`) reach the database through the registered worker account (as the payment and missed-call webhooks do), which may call only `scheduler_*` functions. The credential is the secret address (24 random bytes, shown once, only its sha-256 stored; rotating makes the old one stop at once). The database holds its own caps (20 rows a call, 60 calls a minute and 2,000 leads a day per source) and an unknown or paused address answers 404 with no hint. A hidden `_hp` field catches bots. The embeddable snippet is a plain HTML form with no script.
11. **Portal mails:** parsers for IndiaMART, JustDial, 99acres, MagicBricks and Housing read `Label: value` lines (and label-on-its-own-line tables) from the mail or the same mail forwarded. **They are written from the portals' typical mails, not from real samples**; a mail they cannot read is kept (`lead_unparsed`, cap 200) and shown to the owner, so nothing is lost. The inbound mail provider is not chosen: the per-source address works with any provider that can post a mail to a URL; the one global address (`/v1/lead-intake/mail`) needs `LEAD_INBOUND_SECRET`.
12. **Meta Lead Ads** is behind an interface (`MetaLeadFetcher`): signature check with the app secret, the Graph API fetch with the page token. It is **not run against Meta** (that needs Meta's app verification and a page token); off by default, `fake` for development.
13. **The source tags are one closed list** (`indiamart, justdial, 99acres, magicbricks, housing, meta_lead_ads, website_form, webhook, excel_upload, google_sheet, pasted_list, vcard`) written into `leads.source`, `lead_arrivals`, and the cost table. `public.lead_source_costs` (tenant, source, cost per lead in paise, who, when) is created here with `create table if not exists` and shared with A3.
14. **The estimate** (messages, call minutes, cost) is computed by code from the counts and the workspace plan's prices; the model never calculates money. With no price set the cost is null.

## Consequences
- Migration `20261205090000_dr_lead_sources.sql` adds eight tenant tables (registered in the generic tests, the role matrix, the module-exempt list, the erasure registry for the free-text columns, the data inventory) and two ledgers in the `integrations` schema (no personal data).
- A contact created by a live arrival by the worker account has `created_by` null.
- The old spreadsheet import and `POST /connectors/indiamart/pull` are unchanged; the new IndiaMART route is an alternative with the same window.
- Every non-English line the API sends is English-only: this part has no assistant wording.
