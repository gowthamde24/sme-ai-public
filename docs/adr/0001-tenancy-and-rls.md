# ADR 0001: Tenancy, authorization and audit (T002)

Status: accepted for milestone 1 (database). API and web integration follow in later T002 milestones.

## Decisions

1. **Authorization lives in the database.** `public.memberships (tenant_id, user_id, role)` is the single source of truth. Roles (`owner`, `admin`, `sales`, `viewer`) are not stored in JWT claims, so removing a member takes effect on the next request rather than at token expiry. `user_metadata` is user-editable and is never trusted.
2. **RLS is enabled and forced on every table; default deny.** Policies are `TO authenticated` only, and `anon` holds no privileges. Policies call helpers in a private `app` schema (`is_tenant_member`, `has_tenant_role`, `shares_tenant_with`). The helpers are `SECURITY DEFINER` with `search_path = ''` and take no user argument: the subject is always `auth.uid()`. The `app` schema is absent from `[api].schemas`, so PostgREST does not expose it.
3. **Column-level grants limit what can change.** Clients can update only `tenants.name`, `memberships.role` and `users.display_name`. `tenant_id` is immutable on every tenant-owned table, via a reusable trigger (`app.forbid_tenant_id_change`) that holds even for the table owner.
4. **Privilege escalation is closed in policy and trigger.** An Owner manages every membership. An Admin manages **only `sales` and `viewer` rows**: an Admin cannot add, demote, promote or remove an Admin or an Owner, and cannot change or remove their own row (USING judges the row as it is, WITH CHECK judges it as it would become). A tenant can never lose its last Owner (trigger, serialised by a row lock on the tenant). Authority is per tenant: a user who is Owner of A and Viewer of B has no extra rights in either because of the other (tested in `08_multi_tenant_user.test.sql`).
5. **Tenants are created only by `public.create_tenant(name, slug)`.** It is `SECURITY DEFINER`, validates its input, creates the first Owner membership atomically, and is idempotent for the tenant's Owner. Clients have no INSERT or DELETE privilege on `tenants`.
6. **Audit is written by database triggers, not application code.** `audit_events` records tenant, actor (JWT subject, or `system` when there is none), action, entity, `request_id` (client-supplied `X-Request-Id`, capped at 100 characters in the writer and by a CHECK constraint), and full `old_values` / `new_values`. Owner and Admin can read their tenant's events. No client can write them. UPDATE, DELETE and TRUNCATE are blocked by privilege and by trigger. The FK to `tenants` is `ON DELETE RESTRICT`.
7. **T002 uses no service-role key.** Nothing in the repository holds it. The API (next milestone) will act with the caller's own JWT so RLS always applies.
8. **A catalog guard test polices future tables** (`supabase/tests/database/06_catalog_guards.test.sql`). Any public table with a `tenant_id` column must have forced RLS, a policy, a NOT NULL FK to `tenants`, a leading `tenant_id` index and the immutability trigger. `SECURITY DEFINER` functions must pin `search_path`. Views must be `security_invoker`. `anon` must hold no grants.

## Known limits and follow-ups (accepted for now)

1. **BYPASSRLS dependency.** In Supabase the `postgres` role (which owns every object and runs all `SECURITY DEFINER` functions here) and `service_role` have `BYPASSRLS`; `FORCE ROW LEVEL SECURITY` does not constrain them. The audit triggers and the membership helpers rely on this, so they read and write across tenants by design. Consequences: (a) a bug in any `SECURITY DEFINER` function is a cross-tenant bug, which is why the catalog guard pins `search_path`, restricts who may execute them, and the allow-list of client-callable functions is explicit; (b) the service-role key is total compromise, so T002 uses none and later tickets must ask first; (c) moving to a deployment where these roles lack `BYPASSRLS` would need explicit policies for the trigger paths.
2. **Last-owner rule vs user deletion.** `memberships.user_id` cascades from `users`, which cascades from `auth.users`. Deleting an account that is the sole Owner of a tenant is therefore refused by the last-owner trigger (the cascade raises 23514). That is intended (no orphaned tenants), but a future account-deletion flow must first transfer ownership or run a tenant-closure workflow. Memberships of other roles are removed with the user and audited as `system` or the acting user.
3. **Audit rows vs erasure of personal data (DPDP).** `audit_events` is immutable and `old_values` / `new_values` hold whole membership and tenant rows. They contain ids, roles and tenant names, no email, and `actor_user_id` is a bare uuid with no FK so history survives a user's deletion. A future erasure request would conflict with immutability. Before any real customer data: decide the retention period, whether actor ids are pseudonymised on erasure (a privileged, audited procedure that is the only sanctioned exception to append-only), and keep personal data out of `old_values` / `new_values` (never add email or phone columns to audited tables without revisiting this).
4. **Policy cost per row.** Every policy calls a `SECURITY DEFINER` helper that probes `memberships`. Calls are wrapped in `(select ...)` so Postgres can evaluate them once per statement, and `memberships (tenant_id, user_id)` / `(user_id)` are indexed, but this is unmeasured. **Before T003** benchmark with `EXPLAIN (ANALYZE, BUFFERS)` on realistic volumes (many tenants, ~10^5 rows in a tenant-owned table) for select, join and write paths, and confirm the helper is evaluated as an InitPlan. If it is not, fall back to a `tenant_id in (select ...)` form or cache membership in a per-statement setting.
5. Audit is "append-only style": the table owner or a superuser can still disable triggers. A hash chain or external sink is deferred.
6. Tenant deletion and tenant data export are deferred; the audit FK deliberately blocks a naive delete.
7. Invitations by email, MFA, and rate limiting are out of scope for T002.
8. An Admin cannot remove themselves; leaving a tenant as an Admin currently needs an Owner. Revisit if the product needs self-service leave.
