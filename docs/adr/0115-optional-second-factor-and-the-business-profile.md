# ADR 0115: the second factor is optional, sensitive actions need a recent sign-in, the Owner edits the business profile (job DT, the owner's first real sign-in)

Status: built on branch `api/dt-first-run` (28 Oct 2026), from `main`. Source: the owner's words after the first real Google sign-in (fix-first-run.md): "We don't need authentication again, Gmail is enough", "once I set the business name I can't edit it, so the voice assistant says the wrong business name", and the 20:14 additions (two-factor optional for everyone, sensitive actions need a recent sign-in, profile pictures). Supersedes ADR 0016 where they differ.

## Decision
1. **The second factor is optional for everybody** (Google, Facebook and e-mail alike): never asked at sign-up or at setup. `app.require_aal2()` keeps its name (111 call sites) and changes meaning: (a) a person who TURNED A SECOND FACTOR ON (a verified authenticator in `auth.mfa_factors`) must have entered it in this session (`aal2`); (b) the person signed in RECENTLY: the newest sign-in time in the signed token (the newest `amr` timestamp, else `iat`) is within 10 minutes. A refusal is still SQLSTATE `SM306` with the sentence clients and tests know; a token with no sign-in time is refused (fail closed).
2. **Why `amr`, not `iat`:** a token refresh makes a new token (new `iat`) but not a new sign-in; the `amr` entries carry the time of each sign-in method (password, Google, a code). Supabase puts no `auth_time` claim in the token; this is the equivalent.
3. **The API asks (b) first** (`require_tenant_role(strong=True)`: Owner and Admin only, after the role is proven): 403 `mfa_required` with `reason: "recent_sign_in"` (the screen asks them to sign in again: Google again, or the password). When the database refuses for the second factor the code stays `mfa_required` (no reason, or `second_factor`): the screen asks for the code. One error code, so no client breaks.
4. **The client-write trigger on `memberships` and `tenants`** asks the same two halves; it is a security invoker, so the arithmetic is repeated in it and the second-factor half goes through `app.my_second_factor_on()` (a definer helper that answers for the caller only; the one new `app` function a client role may run, allow-listed in the catalog guard).
5. **`GET /v1/account/security`** now says `second_factor: "optional"`, `second_factor_on`, `signed_in_at`, `recent_sign_in` and `provider`. Turning the authenticator on and off is Supabase's own call from the browser (enrol / unenrol); the Auth server itself demands `aal2` to remove a verified factor, which this ADR does not change. The demo logins keep their authenticator: it is simply no longer needed unless it is on (and it is on for them, so they are still asked for the code on sensitive actions).
6. **The business profile** (`GET`/`PATCH /v1/tenants/{t}/workspace/profile`): name, business type, city, phone, languages, logo. Only the OWNER writes it, with NO second factor and NO recent sign-in (fixing a name is not a risky act). The name is the workspace's own row: everything that renders it (greeting, previews, call and WhatsApp openings, the menu header) reads it live; the voice preview's cache is keyed by the spoken text, so a renamed business is heard under the new name at once. Audited (`workspace.business_saved`: the keys changed, never the values).
7. **The business type** is a pack. "Other" is the new data-only pack `general_business` ("Other business", a generic Lead Desk template; the pack id `other` would collide with the word in every file the pack-id lint scans). The API takes `type: "other"` plus `type_label` (2 to 60 characters, the Owner's own words) and maps it in the database. A change inside the Lead Desk types and Other is free. **Out of a deep pack** (one whose modules include the catalogue, orders or fees) only when none of its records exist; **into a deep pack** only when the business has no leads (its screens would not show them). Otherwise 409 `type_change_refused` with a closed `reason` (`pack_data_present`, `lead_data_present`, `unknown_type`; SQLSTATE `SM791`). This departs from "moving between packs is an operator act" (ADR 0084) by the owner's decision; the source of the choice is `owner` in `packs.workspace_pack`.
8. **Members' own profile and pictures:** `workspace.member_profiles` (name, language, picture) and a private per-business bucket `img-<tenant>` with storage rules: every member reads it, the Owner and Admin put the logo, every member puts and removes THEIR OWN picture (`member/<their id>/…`). The API re-draws every upload server side (Pillow: JPEG, at most 1280 px for the logo and 320 px for a picture, all metadata dropped, 5 MB and 40 megapixels at most, jpeg/png/webp only). The Google photo is the default: a Google address (`*.googleusercontent.com`) read from the sign-in, never another host.
9. **The voice preview** (`GET /ai-assistant/voice-preview`, `/text`): the opening line with the workspace's REAL assistant and business names, then one reply (Tamil and Malayalam: the opening only, until a native reader has written the reply), in the chosen language and way of sounding; same cache, six a minute and daily character cap as the listening sample; never a recording.

## Consequences
- pgTAP: the session helper gives a test token a sign-in time (`iat`); `tests.as_aal('aal1')` now means a password-only session that signed in an hour ago (so every old "refused at aal1" test keeps its meaning), `'absent'` has no sign-in time; `tests.as_signin_age(seconds)` sets it directly. Test 130 covers the new rules; 47 is unchanged in text.
- Tests that counted the packs (twelve) now count thirteen.
- Open for the owner: whether a person who turned the authenticator on should be asked for the code at EVERY sensitive action (today yes, once per session) or only the first time in 10 minutes; the real Telugu/Hindi/Kannada reply lines of the voice preview (hi and kn are drafts); a native review of the `general_business` words.
