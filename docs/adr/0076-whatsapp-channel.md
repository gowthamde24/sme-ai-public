# ADR 0076: WhatsApp (Cloud API) behind the outbox

Status: accepted for the local stage (job BR, 2026-10-12). **Nothing is connected to Meta, no account exists, nothing is bought.** Real sending is switched on only by environment variables the owner sets (ADR 0017: a paid or external dependency needs the owner's written approval first). Branch `api/br-whatsapp`, built on **`api/bo-phone-contacts`** (which is built on `api/bi-integrations`): it needs BO's phone-only contacts and BI's `integrations` schema. Rebase after those are merged. Migration `20261117090000_br_whatsapp.sql`; pgTAP `86_br_whatsapp`; code in `services/ai-api/app/whatsapp/`.

## Context
ADR 0066 made every outgoing message a row that a deterministic policy decides, behind a channel-adapter port with only a local fake. Customers reach a saree shop on WhatsApp. This ADR adds the real channel (Meta's WhatsApp Business Platform, Cloud API), the way messages come IN (a webhook), a chat inbox for the team, and the groundwork for onboarding a shop's own number (Embedded Signup). Facts about Meta's API were read from Meta's own pages on 2026-10-12 (sources at the end); where a page did not say, this ADR says so.

## Decisions
1. **One adapter, `WhatsAppCloudAdapter`, behind the existing port** (`OUTBOX_ADAPTER=whatsapp`; `fake` stays the default). The database decides everything it did before (policy, blocks, quiet hours, kill switch, daily limit, first-message disclosure). The claim now also hands the adapter what a real channel needs: the attempt number, the number to send from, whether the customer's 24-hour window is open, and the APPROVED template of the message's kind and language (`app.wa_send_context`). The adapter sends: **text** inside the window (photos first, as `image` messages from the BB signed URLs, the text as the first photo's caption when it fits 1,024 characters); a **template** outside it (the message text is the template's one variable, cleaned of new lines and runs of spaces); otherwise it refuses with a closed code (`window_closed`, `template_required`). Meta's refusals map to the outbox's closed codes; a busy or unreachable Meta (429, 5xx, network, 130429, 131056) is **transient**: the message is not marked, its claim lapses and it is offered again, up to 5 attempts, then it is marked failed.
2. **Idempotency, honestly.** Meta's send documentation describes no idempotency key (checked on the send-messages pages), so none is used. Duplicates are avoided by (a) the database claim (one worker at a time, a lease), and (b) the message id, which travels as `biz_opaque_callback_data` ("<id>" for the message, "<id>:<n>" for its photos); Meta returns it in the status webhooks. If the API never learnt the answer of a send (a crash between the send and the mark), the first status webhook that carries the id records the message as SENT with its WhatsApp id (`wa_ingest_status`), so its lapsed claim is not sent again. **Residual risk:** between a send and that webhook (seconds, normally) a crash can repeat a message; a message with several photos is not atomic (the first photo may be sent twice if the second fails). Both are rare and visible in the thread.
3. **The webhook** (`GET/POST /v1/webhooks/whatsapp`, public). GET answers the verification handshake with the verify token. POST checks `X-Hub-Signature-256` = `sha256=` + HMAC-SHA256 of the **raw body** with the app secret (constant-time compare); anything else is 401 and counted against the caller's address (20 a minute, then 429); the body is capped at 3 MB and 1,000 events (Meta's own limits); a good one is allowed 1,200 a minute per address. Meta retries a failure for days and may batch, so every event is idempotent on its WhatsApp message id; a data-layer failure answers 5xx so Meta retries. Unknown number ids and a closed real-data gate are acknowledged and counted as ignored (a retry would never succeed).
4. **No person is behind a webhook, so a dedicated, least-privilege account is.** The *channel principal* is an ordinary account registered by the operator in the database (`app.operator_register_channel_agent`), belonging to no workspace (a trigger refuses a membership), with no table rights; its only power is three functions (`wa_account_for`, `wa_ingest_inbound`, `wa_ingest_status`), each of which re-checks it. It cannot read a conversation, an account or anyone's data, and no person's function accepts it. The API signs in as it from `CHANNEL_AGENT_EMAIL` / `CHANNEL_AGENT_PASSWORD` (environment only), the same pattern as the scheduler's principal (ADR 0068).
5. **Inbound is untrusted content** (non-negotiable 6). A message becomes: a contact (found by the oldest live holder of the number, any stored form; else made from the WhatsApp profile name and the number, with a generic company because a lead needs one — named after nothing personal, since an erasure never touches a company), a lead (the contact's newest live one, else a new one sourced `whatsapp`), the **opt-in** (the customer wrote to us; granted with a ledger row naming the message by hash; never over a suppression), and an **enquiry** on WhatsApp (this is also what opens the 24-hour window the outbox policy already read). Text is cleaned (control, zero-width and direction-override characters out, NFC, 4,000 characters) and **never obeyed**: nothing in a message can approve, send, change a price or switch anything; it is stored words and nothing else. Media from the customer is not downloaded (stored as "[image]").
6. **STOP.** A message that IS (whole message, after trimming and punctuation) a stop word in English, Hindi, Telugu, Kannada or the same in Roman letters suppresses the contact in the same call (`opted_out`, WhatsApp consent withdrawn, one ledger row each, the number's key suppressed by the existing triggers, pending messages blocked by the existing trigger). Words that also mean a plain "no" (వద్దు, ಬೇಡ, "end", "cancel") are left out on purpose. The list is a first draft that a native reader of each language should check. A number already on the suppression list (a key suppressed earlier) arrives as a contact **created flagged**: never granted consent, never contactable, its message still kept. The Owner lifts a suppression with the existing route; a message never does.
7. **Suppression keys and erasure are unchanged.** The number's HMAC is made in the API (the key never reaches the database) and recorded for every contact made or found without one. Erasing a contact made by WhatsApp works as for any contact (proven in pgTAP 86 section J).
8. **The real-data gate stays closed** until the operator opens it: a real number is not stored while it is closed (the answer says `gate_closed`, the event is not marked handled, so it is accepted when the gate opens). Local tests use `+00` numbers.
9. **Delivery statuses** (sent, delivered, read, failed) are kept per message (`integrations.wa_message_status`: the furthest step wins, the times of every step are kept, a failure keeps a closed word for Meta's numeric code) and shown as steps of the message (`delivered`, `read`, `delivery_failed`: new kinds in the outbox events, no text). The outbox row stays `sent` (a closed state): delivery is information, not a state change.
10. **The 24-hour window and templates.** Free-form messages only inside 24 hours of the customer's last message (the page says so for "service messages"; the window renews on each message). After that only an approved template. The registry (`integrations.wa_templates`): name, language (our five), category, purpose (visit, followup, order_status, info), body with exactly one `{{1}}` and words around it (Meta does not accept a template that is only a variable — this is written into the check), a status (draft, submitted, approved, rejected, paused, disabled) kept by the Owner/Admin or set after the API asked Meta for review (`POST .../submit` uses `POST /{waba}/message_templates`). The guard is in the database: only an `approved` template is ever named to the adapter; an edit resets to draft; a template under review is not edited. Meta's approval webhook is **not** parsed (its shape was not confirmed): the status is set by hand.
11. **The business's number** (`integrations.whatsapp_accounts`, one per business): WABA id, phone number id (unique, so a number cannot be claimed by two businesses), display number, the **coexistence** flag, and `token_ref` — the NAME of the secret that holds the access token (`WHATSAPP_ACCESS_TOKENS` is a JSON map name to token; `WHATSAPP_ACCESS_TOKEN` the default). **No token is ever stored, returned, logged or accepted by a route.** Saving and switching on are the Owner's, with a second factor; a changed number is not live until switched on again.
12. **Conversations API** for a chat inbox: a list (one row per customer who wrote or was written to: name, company, last message, direction, unread, the window and when it closes, stopped), a thread (customer messages and ours with each one's state and delivery), and "mark read". A reply is the existing outbox submit with category `reply_to_inbound` (the policy and the approval stay the outbox's). Owner, Admin and Sales; a Viewer reads none (a message can hold a price).
13. **Embedded Signup groundwork.** Embedded Signup returns the WABA id, the phone number id and a code to exchange for a business token; the server must exchange it, register the number (not for coexistence: the number is already registered), and subscribe the app to the WABA's webhooks. Built: where the results are stored (decision 11). Not built (needs a Meta app, App Review and a Tech Provider status): the code exchange, the number registration, the `subscribed_apps` call and the JavaScript SDK on the web. Migration notes for later: add `business_id`, `token_expires_at` and a `signup_event` log to `whatsapp_accounts`; switch `token_ref` to a secret-manager reference per tenant; Embedded Signup v2 is deprecated on 15 October 2026 (Meta's coexistence page), so build v4 only.

## Consequences
* New SQLSTATE `SM621` (not in a state that allows this). New failure codes on the outbox: `window_closed`, `template_required`, `recipient_unreachable`, `rate_limited`, `not_configured`. New step kinds: `delivered`, `read`, `delivery_failed` (their `reason` is a closed word; `reason_text` its fixed sentence).
* The dispatch loop gained transient failures (`SendResult.retry`) and the attempt number; `OUTBOX_ADAPTER` accepts `whatsapp` (it needs a token in the environment or the process refuses to start).
* Not in v1: reading the customer's photos and voice notes, interactive buttons we send, broadcast/marketing campaigns, per-tenant app secrets, pricing/billing awareness, Meta's quality rating and messaging-limit tiers, history sync for coexistence (`smb_message_echoes`, `history`).
* Coexistence caps throughput at 20 messages a second (Meta); the adapter does not pace itself (a busy answer is retried).

## Update, job DU (28 Oct 2026): staging runs it against the Cloud API v25.0
Staging turns the adapter on (`OUTBOX_ADAPTER=whatsapp` on the API; the worker's automatic sending stays on the fake adapter) with Meta's test number. Decisions: (1) a **test fence**, `WHATSAPP_ALLOWED_RECIPIENTS`: when set, the adapter refuses (`rejected`, nothing leaves, the number is not logged) any recipient not on the list, and set-but-empty refuses all, so staging fails closed; unset (production) means no fence. (2) The verify token and the channel account are mounted by `deploy/staging.sh` only when their secrets exist, so a deploy never fails on a missing one. (3) Webhook address: the staging API's own address (`staging.stack19.com` does not forward `/v1`). Set-up and checks: docs/runbooks/whatsapp-staging.md.
