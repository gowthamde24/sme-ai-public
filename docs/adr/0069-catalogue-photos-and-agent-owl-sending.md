# ADR 0069: the saree catalogue, private photo storage, photos in the outbox, and Agent OWL's two catalogue tools

Status: accepted for the local stage (job AY, 2026-10-12). Builds on ADR 0066 (the outbox and its policy), ADR 0067 (store visits), ADR 0068 (the worker; amended by this job: approved = send), ADR 0013 (agents act in a person's name) and ADR 0017 (local first). Nothing is deployed; the only channel is the local fake; no real product photo exists in the repository.

## Context
A wholesale saree business shows customers sarees, not SKUs: a picture, a fabric, a colour, a rough price. Customers ask on WhatsApp "send me some red Kanchi pattu for a wedding". Until now the system could talk (the outbox) but not show. The owner asked for a catalogue that Agent OWL can search and send, under the same send policy as every other message, with photos kept in the local Supabase Storage (no new account).

## Decisions
1. **Items.** `catalogue_items`: name, fabric (a closed list: Kanchi pattu, Dharmavaram silk, soft silk, cotton silk, Banarasi, Mysore silk, Uppada, pure cotton, georgette, other), 1 to 4 colours (a closed palette), zari (none, light, rich), a short border description, up to 4 occasions (wedding, festival, daily, party), a **price band** (under 5k, 5-10k, 10-25k, 25-50k, above 50k), a stock status (in stock, few left, made to order) and an active flag. An **exact price** (`price_paise`) exists only if the Owner sets it; it needs a second factor; an Admin cannot, and the agent never can (non-negotiable 4). Every member reads the catalogue (it is what the shop shows); Owner and Admin edit; nobody writes a table directly (definer functions, role first). Rows are never deleted (deactivate). Audit as for the other tables; the catalogue holds no personal data, so no erasure entry is needed.
2. **Photos.** `catalogue_photos`: 1 to 8 live photos per item, a REFERENCE (bucket, path, thumbnail path, size), never bytes. A removed photo stays as a row (a sent message may refer to it) but is no longer shown, counted or sent. An item can be **active only with at least one live photo** (a trigger and the functions), and its last photo cannot be removed while it is active.
3. **Storage.** The LOCAL Supabase Storage service, which this job turns on in `supabase/config.toml` (it was off; `supabase stop && supabase start` once). **One private bucket per business** (`cat-<business id>`, 5 MB, jpeg/png/webp), made on first use by `catalogue_ensure_bucket`. Row-level security on `storage.objects`: a member of the business reads its bucket (that is what lets the API sign a URL in the caller's name); Owner and Admin add and remove files there; no other bucket is touched. The API holds no service key: every storage call carries the caller's JWT. **Paths are derived by the database** from the item and photo ids (`<item>/<photo>.jpg` and `_t.jpg`); a client never names one; `catalogue_photo_add` checks that both files really exist in the business's bucket as jpeg. Photos are shown by **signed URLs that expire in 10 minutes**; there is no public URL.
4. **Server-side processing (a new dependency: Pillow).** An upload is the raw body of a POST with its Content-Type. The server decides the type from the BYTES (jpeg, png, webp; not animated), refuses more than 5 MB or 40 megapixels before decoding, applies the camera's orientation, **drops every piece of metadata** (EXIF including GPS location, camera, time; XMP; colour profile; comments) by building a fresh image from the pixels, flattens transparency onto white, and stores a JPEG at most **1280 px** on its longest side (WhatsApp-friendly) and a **320 px thumbnail**. The pixels of the original are not kept. *Why Pillow:* resizing, orientation and metadata removal are not possible with the standard library; Pillow is the standard, free, widely audited library for it (no network, no account, no cost), pinned in `pyproject.toml`. *Honest limit:* an Owner or Admin can write a file straight into their own business's private bucket with their own JWT (the storage rule allows it) and register it; the database checks it is a jpeg of the right paths but cannot check that metadata was stripped. That is self-harm of their own photos, not another business's data.
5. **Matching.** `catalogue_search` is plain SQL and deterministic: fabric, ANY of the given colours, ANY of the given occasions, any of the given price bands, in stock (in stock or few left). Fixed order: in stock, few left, made to order, then name, then id; paged. Only active items with a live photo are found (the Owner and Admin can ask for the rest). **No model, no vision.** `GET /catalogue/items` is the same function.
6. **Photos in the outbox.** `outbox_message_media` holds REFERENCES (message, photo, place 1 to 4); the message row is unchanged. The policy is unchanged and reads the **caption**: a price band or an amount in it is money, so the message waits for a person; photos with no price go by themselves **only when the business switched automatic sending on**, and otherwise wait for the Owner. A photo must be a live photo of an **active** item of the same business (a removed, inactive or foreign photo is refused). A claim hands the channel each photo's bucket, path and type; the **local fake adapter records them**; a real channel will fetch through a signed URL (not built; the claim runs as the worker's principal, which cannot sign, so a real adapter needs a minting step, listed in the checklist). A photo removed after a message was queued is simply not handed over.
7. **Keep a record.** `keep_record` on `POST /outbox/messages` makes the database log the **lead touch at the moment the message is really sent** (`outbox_mark`), never when queued and never for a blocked or failed message. The touch is made in a sub-transaction that swallows its own failure (the 500-touch cap, a concurrent change): bookkeeping must never make a delivered message look undelivered and so be sent twice. It also discards follow-up drafts the new touch supersedes, as `record_touch` does. The flag is part of the request hash (a retry that drops it conflicts).
8. **Agent OWL: two tools.** `find_catalogue_items` (read) takes fabric and colour as plain words that the code matches to the closed lists (a few spellings: Kanjivaram, Kanchipuram...), an occasion, a price band and in-stock; it returns up to 6 items as citable sources (a band in words; an exact price, only if set, in the rupee text the answer-checker allows). `send_catalogue_items` (action) queues **one** WhatsApp message with the **cover photo** of 1 to 4 items and a short caption in the **customer's** language (checked by script like a reply draft), through the same outbox function a person uses, as `source assistant`, category `info`, under the caller's own token. It names no phone, status, tenant or price; it dispatches nothing; the same ask twice is one message. A caption with an amount waits for the Owner (policy); the model cannot lower that bar. **This is the first assistant tool that submits to the outbox**; it is allowed because the outbox policy is the explicit approval path non-negotiable 3 asks for, and two standing guards were amended on purpose: `test_assistant_units.py` now allows exactly one tool with "send" in its name and one field named `price_band` (a closed enum filter), and `test_migration_copies_ay.py` pins the database copies.
9. **Tool budget.** The two tools add about 320 estimated tokens to every model call (the tools are sent with every question). The measured size of a question went from about 3,450 to 3,705-3,986 tokens and of a call from under 2,000 to 1,855-2,190; the ceilings in `tests/integration/test_assistant_tokens.py` are raised to 4,050 and 2,250 for exactly this, and the finder was slimmed (plain-word fabric and colour instead of long enums). **Risk:** a free-tier model with a small tokens-per-minute allowance has about 13 % less room per question.
10. **Small gaps found by the web (job AV report).** (b) `POST /leads/{id}/draft-message`: Agent OWL writes one suggested WhatsApp message in the lead's language (a stated language, else the script of the customer's last message, else English) with an English gloss, in a single model call with no tools. It is a **run of the assistant**: the switches and limits of `assistant_begin_message` apply, the worst-case cost is reserved before and the usage recorded after (it counts against AI usage), the customer's data reaches the model only as untrusted data between a per-run delimiter, the answer is checked by code (language by script, no amount, no promise; one repair retry, both calls paid) and the run keeps the words (provenance). It is a suggestion: not saved as a draft card, not sent; the person edits it and sends it through the outbox. (c) `GET /leads/search`: by company name, contact name, or the END of a phone number (4+ digits), newest first, paged; it returns the contact's short name and the last four digits only. (d) Today's `waiting` count includes the visits Agent OWL proposed (booked, from the assistant, within 61 days; Owner, Admin and Sales decide them), so the menu badge equals the cards; the list of items is unchanged. **The web must stop adding its own count of proposed visits to `waiting`, or it will count them twice.**
11. **The AW amendment** (approved = send) is ADR 0068's addendum.

## Consequences
* New: migrations `20261110090000_ay_catalogue.sql`, `…090100_ay_outbox_media.sql`, `…090200_ay_lead_search_today.sql`, `…090300_ay_assistant_sources.sql`; tables `catalogue_items`, `catalogue_photos`, `outbox_message_media`; column `outbox_messages.keep_record`; storage rules; API `app/catalogue/`, `app/leadtools/`, `app/assistant/draft.py`; `make seed-demo-catalogue`; pgTAP 80; runbook `docs/runbooks/catalogue-local.md`.
* `public.outbox_submit` changed signature (two trailing parameters with defaults), so its old 10-argument form was dropped and every caller (visits, offer-a-visit, the scheduler's reminders) keeps working through the defaults.
* A plain TRUNCATE of `catalogue_items`, `catalogue_photos` and `outbox_messages` is refused by foreign keys (0A000) before a guard runs; CASCADE reaches the guards (42501).
* The local Storage service is now part of the dev stack (`supabase start` pulls its image once); CI starts it too.
* Files of removed photos stay in Storage (a message may point at them); an orphan clean-up is not built.
* Telugu, Hindi, Kannada and Tamil captions written by the agent are model text in the customer's language: the owner reads them like any draft; the fixed templates of visit messages remain the only wording that is ever pre-approved.

## Addendum: what is reachable directly (CI fix)
`tests/integration/test_order_direct_postgrest.py::test_nothing_is_reachable_that_should_not_be` counted the public SECURITY DEFINER functions with "order" in their name and expected 3 (the order engine's `create_order_from_quote`, `create_order_policy_version`, `record_order_event`). It found 4: **`public.catalogue_photos_reorder`**, which matches only because "reorder" contains "order". It is meant to be callable by a signed-in person: it puts the photos of one catalogue item in a new order, proves the Owner or Admin role of the business named in the call before it does anything (anyone else, and the anonymous caller, are refused), and reads and writes only that business's own catalogue rows (no personal data, no other business). It has nothing to do with orders. Nothing was closed, because nothing was open that should not be; the guard now **names** the four functions (an exact list, so a fifth fails it) and also checks that the anonymous caller and a Sales member are refused (`42501`) by this one. No new item is reachable through Storage or a table beyond what ADR 0069 decision 3 describes (the per-business bucket and its member-read, Owner/Admin-write rules).
