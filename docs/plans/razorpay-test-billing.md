# Razorpay billing in TEST mode (C12): what is built, what the first run must prove, what is open

Owner instruction: Razorpay TEST billing, mocked until the owner stores the TEST keys; `sk_live_` / live billing stay OFF everywhere. Decisions marked **(C1)** were made under the standing rule of 13 Nov 2026; the owner can reverse them.

## Built (PR for C12, 13 Nov 2026)
- `app/billing/razorpay.py` `RazorpayBilling`, behind the existing `BillingProvider` interface; `BILLING_PROVIDER=razorpay` plus `BILLING_RAZORPAY_KEY_ID` / `_KEY_SECRET` / `_WEBHOOK_SECRET`. **Only `rzp_test_` keys are accepted; a live key stops the process at start.** The default stays `fake` (staging and production).
- Checkout flow (Razorpay's own page collects the payment method; our servers never see a card or UPI detail): `begin_checkout` creates the Razorpay plan once (found again by its notes `stack19_plan=<plan>:<price>`) and a subscription whose notes carry our tenant id; the browser returns payment id, subscription id and signature; `create_subscription` checks the signature (HMAC-SHA256 of `<payment_id>|<subscription_id>` with the key secret) and records the subscription. `checkout_ref` = `<subscription_id>.<payment_id>.<signature>`.
- Cancel (at once, or at the end of the cycle; safe to repeat). Webhook `POST /v1/webhooks/razorpay-billing`: signature over the raw body with the WEBHOOK secret, `subscription.charged / pending / halted / cancelled` become `charge_succeeded / charge_failed / halted / cancelled`, event id from `X-Razorpay-Event-Id`, applied by the registered worker account, once per id (the database already guarantees it). 401 on a bad signature, 404 unless the provider is Razorpay.
- Tests: `tests/test_razorpay_billing.py` (10) against recorded-shape fakes. **It has not run against Razorpay's servers: the first run with the owner's test keys is the real check of this file.**

## Decisions (C1)
1. **Plans and prices: the OWNER'S FINAL PRICING of 13 Nov 2026 (project doc `decision-plans-and-pricing.md`), which replaces my earlier "keep the seven plans".** Pay as you go ₹499/month (business number + app) + ₹5/min; Sales Assistant ₹1,999/month, number included, 500 min, then ₹4.50/min; Sales Assistant + Lead Finder ₹5,999/month, up to 3 numbers, 1,500 min, then ₹4/min, Lead Finder unlimited (fair use). Everyone: 1 free Lead Finder search a month (PAYG extra searches about ₹49), billing per 30 s, unanswered calls free, yearly = 2 months free, launch prices locked 12 months, +18% GST on invoices, WhatsApp optional at Meta's cost with no markup, ₹50 free usage on signup with no card. **This PR builds the Razorpay ADAPTER those prices run on (checkout, signed webhooks, cancel); the catalogue itself (`packages/plans/plans.json` v5), the ₹ wallet, per-30-s metering, GST invoices and the free ₹50 are the NEXT PRs (billing v2, tracked in the master list), so until they merge the old catalogue has no prices and `begin_checkout` refuses with `plan_has_no_price`. Nothing is charged by accident, and staging stays on the fake provider.**
2. **First charge date:** the subscription's `start_at` is fixed when it is created (Razorpay has no call to move it). With the final pricing there is NO 14-day card trial (the free start is ₹50 of usage with no card), so a subscription starts charging at checkout (`trial_days` 0 in billing v2); the 14-day placeholder in `begin_checkout` is the old model and is replaced there. Yearly plans are a second Razorpay plan (`period: yearly`) at 10 months' price.
3. **Webhook secret and key secret are separate** and both entered at a hidden prompt; the workspace payment-link keys (`RAZORPAY_*`) are a different thing and stay as they are.

## Open (not built, in this order)
1. **Owner step to run the first test** (needs the owner): in the Razorpay dashboard in TEST mode create a key pair and a webhook to `https://<staging api>/v1/webhooks/razorpay-billing` with events `subscription.charged`, `subscription.pending`, `subscription.halted`, `subscription.cancelled`; then `gcloud secrets create ...` for the three values at a hidden prompt (the command is in `docs/runbooks/production-owner-steps.md` style; C1 provides it when asked) and set `BILLING_PROVIDER=razorpay` on staging.
2. **Web checkout:** the endpoint is BUILT: `POST /v1/tenants/{t}/billing/checkout {plan_id}` (Owner) -> `{provider, key_id, subscription_id, plan_id, amount_paise, currency}` (fake provider: `key_id` and `subscription_id` null; errors `plan_unknown`, `trial_already_started`, `plan_has_no_price`, `billing_unavailable`). The web (C2) opens Razorpay Checkout with it and sends `checkout_ref = "<subscription_id>.<payment_id>.<signature>"` to `POST /billing/trial` (the body now takes dots and up to 200 characters).
3. **One-time payments** (`charge_once`): wallet top-ups and the PAYG ₹499 monthly fee are Razorpay ORDERS (a server-created order, the browser's Checkout pays, a signed return, then the webhook `payment.captured` credits the wallet once per payment id). Raises `NotSupportedError` today: billing v2.
4. **Plan change mid-cycle** (`change_plan`): up and down, prorated, taking effect cleanly; a downgrade keeps the data (Razorpay's subscription update with `schedule_change_at` plus our own proration line on the invoice). Raises `NotSupportedError` today: billing v2.
5. **GST invoice:** Razorpay issues invoices for subscriptions (`invoice_id` on `subscription.charged`); mapping it to our GST invoice (ADR 0092 addendum) and the e-mail is open. Retries and the grace period are Razorpay's own schedule (we only apply the events); the 7-day grace in the fake provider is the model, to be set in the dashboard.
6. UPI AutoPay / e-mandate are chosen on Razorpay's Checkout page by the owner's account settings, not by our code.
