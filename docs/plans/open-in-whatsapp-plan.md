## 0. What this is, in one paragraph

On an approved quote, a person with the right role gets three things side by side: **Copy text** (exists), **Open in WhatsApp** (new: it opens the person's own WhatsApp with the customer's number and the quote text already typed in; the person presses send themselves) and **I sent it on WhatsApp** (new: records an outgoing WhatsApp touch for the lead, which is what starts the follow-up clock). **This system sends nothing.** There is no API change, no migration and no new dependency: everything below uses endpoints that exist today. If any slice turns out to need one, the rule is to stop and report.

## 1. What the action does

**Today.** An approved quote shows its customer text with a "Copy text" button and the sentence "Nothing is sent by the system. Copy this text and send it yourself, in your own message." (`apps/web/app/app/tenants/[tenantId]/enquiries/copy-text.tsx:13-44`, rendered at `enquiries/quote-panel.tsx:117-128`). The text is fetched on the server for an approved quote only (`enquiries/[enquiryId]/page.tsx:75-81`) from `GET /quotes/{id}/text` (`services/ai-api/app/quotes/routes.py:126-137`), which re-runs the pinned engine on the stored request, checks it equals the stored result, and renders with the pinned `quote_text` (`services/ai-api/app/quotes/service.py:526-582`). The API answers 409 `quote_not_approved` for any quote that is not approved (`service.py:536-541`).

**New.**
1. **Open in WhatsApp**: a plain link on the quote screen that opens `https://wa.me/<number>?text=<the quote text, percent-encoded>`. On a phone this opens the WhatsApp app with the chat and the text ready; on a desktop it opens WhatsApp Desktop or WhatsApp Web (**UNVERIFIED**, section 7). The person reads it and presses send in WhatsApp.
2. **Copy text** stays next to it as the fallback (section 3).
3. **I sent it on WhatsApp**: one button that records "I sent a message to this customer by WhatsApp, now" (section 4).

**Nothing is sent by this system.** The link is the person's own navigation; the system cannot know whether they pressed send, which is why "I sent it" is a separate, honest, manual button. The quote text is the pinned `quote_text` 1.0.0 output, unchanged and never edited or truncated by the link.

## 2. Where the phone number comes from, and how it stays out of text, logs, errors and action results

### Where it lives today

* The number is stored as typed, 3 to 32 characters, with no normalisation (`services/ai-api/app/crm/models.py:66,271`, `supabase/migrations/20261005100100_t003_crm_core.sql:141`). While the real-data gate is closed every phone must start with `+00` (`supabase/migrations/20261012090100_t006b_m2_review_fixes.sql:142`), so every number today is synthetic.
* Any member may read a contact through the API, phone included (`services/ai-api/app/crm/routes.py:54,69-71`: `READERS = ()` means any member, and the contacts entity is read by everyone), and the contacts tab prints it as page text (`apps/web/app/app/tenants/[tenantId]/page.tsx:338`).
* **Every web helper written so far deliberately does not read it**: the add-a-customer client "never renders" it (`apps/web/lib/api/customers.ts:7-8`), the consent client reads the three consent states only (`lib/api/consent.ts:5-6`), and item g read only the contact's id so that the lead page could point at the consent page (`lib/api/lead-contact.ts:4-7`). Item f is therefore the **first web code that reads a phone number for a purpose other than printing it in the contacts table.** That deserves one explicit decision (section 8, no. 1).

### The choice: where the number is put together

There are three ways to get a number into a `wa.me` link:

* **A. A link built in the page.** The server component reads the phone and writes `<a href="https://wa.me/...">`. The number and the full text then sit in the page HTML and in the React server-component payload, in the browser's saved page and in any developer tool. Simple, but it puts the number into every render of the quote screen, for every role that can see that screen.
* **B. A same-origin redirect route (recommended).** The page contains only an internal link, `/app/tenants/{tenantId}/quotes/{quoteId}/whatsapp`. When the person clicks it, the server (not the page) reads what it needs with the person's own token, builds the link and answers **HTTP 302 with `Location: https://wa.me/...`**. The number appears in exactly one place: the redirect response to that one click. There is a precedent for a route handler with the same auth pattern: `apps/web/app/app/tenants/[tenantId]/review/export/route.ts:11-56` (`requireUser`, `fetchTenant`, a role check, then the API call).
* **C. A server action that returns the link.** Rejected: an action result is serialised to the browser and the screen would then hold the number in state, and a script-opened window is blocked by pop-up blockers.

### How plan B keeps the number out

* **Page text and page HTML**: never. The quote panel receives no phone, no digits and no wa.me address as a prop; it renders an internal link whose address is built from two validated ids (the same discipline as `test/guards.test.ts:389-410`, "every href ... is an internal path built from validated ids"). A new guard test extends that rule to the quote panel and adds: no component under `enquiries/` imports the link builder, and only the route does.
* **Server action results**: the "I sent it" action returns the same shape as item g's (`sent-message-actions.ts:17`: `ok`, `channel`, `at`, never a number, an address or API text). The route is not an action.
* **Error messages**: the route never returns text from the API or the database. It answers a failure with a **redirect back to the quote screen with a closed code** (`?whatsapp=consent`, `contact`, `key`, `erased`, `unkeyed`, `no_phone`, `bad_number`, `too_long`, `not_approved`, `unavailable`), and the page maps each code to a sentence of our own wording. The export route does the opposite today (it returns `error.message`, `export/route.ts:52-54`); the new route must not copy that line. A test checks that a canary placed in every API field never appears in any response of the route.
* **Logs**: the API drops the query string from access lines and redacts any path segment that is not a route word or a UUID (`services/ai-api/app/logging_safety.py:1-10,44-60`); the route calls only existing endpoints (`/quotes/{id}`, `/quotes/{id}/text`, `/leads/{id}`, `/contacts/{id}`, `/leads/{id}/followup`), so no new word is logged and the number is only ever in a response body, which that module never logs. The web app's own server logs would show the route's path (two UUIDs). The route logs nothing; a test greps the new files for `console.` and for template strings that contain a phone variable.
* **Referrer and caching**: the redirect carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, and the link is opened with `rel="noopener noreferrer"` in a new tab. The app already sends `Referrer-Policy: strict-origin-when-cross-origin` and `Cross-Origin-Opener-Policy: same-origin` (`apps/web/lib/security/headers.ts:11,19`), so even the default would send WhatsApp only our origin, not the path. The CSP does not restrict link navigation (`lib/security/csp.ts:23,26` restrict `connect-src` and `form-action` only), so a plain anchor needs no policy change.
* **What the route trusts**: nothing from the browser except two ids in the path. The number and the text are read on the server with the person's own token, so a person cannot make the route open a chat with a number or a text of their choosing. It answers 403 for any other site driving the click (`Sec-Fetch-Site` must be `same-origin` or `none`), so a link on another site cannot send a signed-in person to a chat with their customer.

### What the link contains, and who can see it

* **Contents**: the digits of the customer's number in international form, and the approved quote text (customer name, items, quantities, prices, tax, totals, validity). It contains no tenant id, no lead id and no email. It is exactly what the person would otherwise copy and paste by hand.
* **Who can see it**: the signed-in person who clicked (it appears in their browser for an instant and in that browser's history once it opens WhatsApp); the WhatsApp app or WhatsApp Web on their device; and **WhatsApp and Meta**, which receive the number and the text whenever anyone messages through WhatsApp. The lawyer's relayed point that the WhatsApp provider and Meta are sub-processors, and that the privacy notice must say so, applies (`dpdp-counsel-guidance-2026-10-08.md:52-54`). Not seen by: our API (no new endpoint), its logs, the page HTML, the browser's saved page, or the next page the person visits (referrer).
* **UNVERIFIED**: who can read response headers at the future host (a proxy or CDN in front of the app). Nothing is deployed. The Customer Zero hosting stage must check that the redirect's `Location` header is not logged by the host. The pre-pilot checklist already has a row that proxy and CDN logs must drop query strings (`docs/pre-pilot-checklist.md:72`); a **response header** is a different thing, so slice 5 adds its own row.

## 3. Message length

* **What is measured.** The synthetic two-item quote text is 721 characters; URL-encoded it is **1,185** (the rupee sign becomes nine characters, each newline three: `docs/plans/customer-forms-plan.md` findings, section c). The renderer's own bounds allow lines of up to 60 characters and up to 500 lines (`packages/pure/quote_text/__init__.py:10-14`); the worst case encodes to about 271,500 characters. Nothing in the code or any test encodes a quote text today.
* **What is NOT known.** WhatsApp's real limit on the `text` parameter, any limit a browser, Node or a proxy puts on a redirect's `Location` header, and whether every character (the rupee sign, line breaks) survives are all **UNVERIFIED**: no website was called and nothing was opened.
* **Rule for the plan.** Never shorten a quote silently. The route has a cap on the **encoded** text, a named constant. The value in this plan, **2,000 encoded characters**, is a **placeholder of ours, not a WhatsApp fact**; the owner replaces it after a by-hand test (section 8, no. 3). The page already holds the text, so it knows before the click whether the link would be too long and shows a different control, without needing the phone:
  * under the cap: **Open in WhatsApp** (chat with the text ready) and **Copy text**;
  * over the cap: **Open the WhatsApp chat** (the same route with `?chat=1`, a chat with no text) next to **Copy text**, and a plain sentence: "This quote is too long to put in a link. Press Copy text, open the chat, and paste." The person pastes the whole text; nothing is cut.
  The route re-checks the length itself and, if the text is over the cap and `chat=1` was not asked for, redirects back with `?whatsapp=too_long`.

## 4. "I sent it" on a quote: the touch, the retry rule, and exactly when the clock starts

### What it reuses

* The same endpoint and function as item g: `POST /leads/{lead_id}/touches` (`services/ai-api/app/followups/models.py:44-51`: `RecordTouchIn` has only `id`, `direction`, `channel`, `occurred_at`) into `public.record_touch` (`supabase/migrations/20261024090000_t010_part2_followups.sql:829-899`), through the same web client `recordTouch` (`apps/web/lib/api/followups.ts:476-481`).
* **Direction is fixed to outgoing, in the server action, never read from the form** (the item g rule, `sent-message-actions.ts:63-65,81`). The channel is fixed to WhatsApp by the button (so there is no select to leave unselected). The time is the database's "now" (`occurred_at` null means the database clock, `followups.sql:852,884`).
* **The id-per-render retry rule**: the page makes one id per render (`enquiries/[enquiryId]/page.tsx:143,145` do this for `newQuoteId` and `newOrderId`; item g's lead page does it at `leads/[leadId]/page.tsx:101`), the form is keyed on it, and after a saved press it takes a fresh id (`leads/[leadId]/sent-message-form.tsx:22-38`). A second press with the same id is a replay (`followups.sql:859-863`: the same lead, direction, channel and time replays with `replayed: true`); the same id with other content is a conflict (`followups.sql:865`, mapped at `sent-message-actions.ts:51`).
* The action takes the **quote id**, not a lead id: the server fetches the quote (`GET /quotes/{id}`, which includes `lead_id`: `apps/web/lib/api/quotes.ts:85`), refuses unless its outcome is `approved`, and uses that lead. Nothing about the lead comes from the browser.
* The refusal wording is item g's `refusal()` (`sent-message-actions.ts:23-60`). That function lives in a `"use server"` file, which may export only async functions (`test/guards.test.ts:480`), so slice 4 moves it into a plain module that both actions import. Item g's tests keep passing unchanged because behaviour does not change.

### When the clock starts, and what the due list then shows

* **Saving or approving a quote does not start the clock.** A lead appears on the due list only after at least one outgoing touch; without one the engine answers `initial_outreach_required` (`docs/plans/followups-due-candidates-plan.md:43`, condition L1; `docs/plans/t010-followup-cadence.md:45-46`).
* **The clock starts at the moment `record_touch` stores the touch**: the row is inserted with `occurred_at = coalesce(p_occurred_at, now())` (`followups.sql:884-886`). From then `touch_number` is the number of outgoing touches plus one, the anchor is the latest outgoing timestamp, and the next eligible time is `max(last + gap_days[0], last + min_gap_hours, as_of)`, moved forward to an allowed weekday, off holidays and out of quiet hours (`t010-followup-cadence.md:47-57`; the policy fields are `gap_days`, `max_touches`, `quiet_start`, `quiet_end`, `allowed_weekdays`, `holidays`, `min_gap_hours`: `followups/models.py:27-41`).
* **What the due list then shows** for that lead (`apps/web/app/app/tenants/[tenantId]/followups/due-view.tsx:36`): **"Not yet"** with the next eligible time until then, then **"Due now"** when a follow-up draft may be asked for; a reply recorded later turns it into "No follow-up". The follow-up wording is a closed template an Owner or Admin approves, and the person sends it by hand (`customer-zero-intake-gap.md:253`), exactly as today.
* **Facts that follow from the code, worth saying on the screen:** (a) a touch belongs to the **lead**, not to the quote (only a follow-up draft has a `draft_id`: `followups.sql:862` and `customer-zero-intake-gap.md:257`), so the page cannot later say "this quote was sent"; it can say only what the press just recorded; (b) every press is another outgoing touch, so sending a revised quote a second time moves the anchor and uses one of the policy's `max_touches` (a hard cap of 500 touches per lead also exists, `followups.sql:881-883`); (c) an outgoing touch may not be dated before the lead's latest outgoing touch (`followups.sql:874-876`); (d) whether the database itself requires a follow-up policy before recording a touch is **UNVERIFIED**: I read `record_touch` (lines 829-899) and found no policy check there, but the screen has a sentence for the code `no_followup_policy` (`sent-message-actions.ts:48`), so some layer can raise it.
* After a successful press the action revalidates the follow-up page and the due list, not the quote page, so that the success sentence stays (the item g rule, `sent-message-actions.ts:85-87`).

## 5. Consent

### What the database requires today before an outgoing WhatsApp touch is recorded

`record_touch` runs `app.followup_gate(lead, 'whatsapp', lock)` for every outgoing touch (`followups.sql:868-872`). The gate (`followups.sql:417-467`) refuses unless **all** of these hold:

1. the lead has a contact, and the contact exists (`:429-435`; otherwise reason `consent`);
2. the contact is not erased (`:436-438`, reason `erased`) and not suppressed (`:439-441`, reason `contact`);
3. the contact has a **phone** (`:442-444`; no number gives reason `consent`);
4. a **suppression key** exists for the phone (`:445-449`; otherwise `SM221`, which the screen says as "no suppression key yet", `sent-message-actions.ts:46-47`);
5. that key is not suppressed, directly or through another contact that shares it (`:453-461`, reasons `key` and `erased_key`);
6. `app.can_contact(contact, 'whatsapp')` is true (`:462-464`): **`whatsapp_consent = 'granted'`**, a phone present, not suppressed and not archived (`supabase/migrations/20261005100200_t003_consent.sql:269-285`).

The gate is not checked when the person merely opens WhatsApp; it is checked when "I sent it" is recorded. Section 8, no. 6 proposes checking it **before** opening, with the database's own read (below).

### What the owner must record per customer first

* The customer: company, contact name, **phone**, and a lead linked to that contact (the add-a-customer form, `apps/web/app/app/tenants/[tenantId]/customers/new/`).
* A **suppression key** for that phone: the API makes it when the contact is created if its key secret is configured (`customers.ts:32`); otherwise the gate answers `unkeyed` and the owner records keys on the suppression-key page (`sent-message-actions.ts:47`).
* **WhatsApp consent: granted**, on the consent page `/app/tenants/{tenantId}/contacts/{contactId}/consent`: a basis (`explicit_consent`, `contractual`, `legitimate_use`, `other`), an evidence kind (`verbal`, `written`, `email_reply`, `web_form`, `other`) and a short label (`apps/web/lib/api/consent.ts:17-23`; the label pattern is at line 26). The database requires all three for a grant (`t003_consent.sql:123-126`). The consent form starts with **nothing selected** for the status, the basis and the evidence kind (`contacts/[contactId]/consent/consent-form.tsx:47,69,80`, the owner's instruction), and this plan changes none of that.

### What this plan leaves to the written DPDP opinion

Nothing in this plan changes a consent rule, a basis, an evidence kind, a quiet-hours rule or the real-data gate. The relayed points that touch it, all **relayed and unconfirmed** (`dpdp-counsel-guidance-2026-10-08.md`):
* a quote the customer asked for, and a reminder about it, are legitimate uses (point 2, line 23): this suggests such a message might not need recorded consent at all, whereas the database today requires `granted` for every outgoing WhatsApp touch. Which is right, and whether `legitimate_use` is the basis to record, is the lawyer's call (section 8, no. 8);
* consent evidence should be a verifiable digital record and a verbal yes is not enough; the evidence kinds "verbal" and "customer enquiry" change later (point 6 and the "Later" item, lines 36-37 and 107-109). The consent form still offers "verbal" today and this plan leaves it;
* quiet hours: whether they apply to a reminder about a quote, and to WhatsApp at all, is an open question (lines 137-139). Recording a touch does not check quiet hours (they only move the next eligible time, `t010-followup-cadence.md:53-55`); this plan adds no check;
* withdrawal must stop outreach within a reasonable time (point 7); today a withdrawn consent or a suppression makes the gate refuse at once, which is stricter than "24 to 48 hours";
* the privacy notice must name WhatsApp and Meta as third-party platforms (point 11).
Until the written opinion is filed the real-data gate stays closed and every number is `+00`, so none of this touches a real customer (section 7).

## 6. Roles and states

* **Owner, Admin, Sales**: see all three controls on an approved quote. The quote screen is loaded only for these roles (`enquiries/[enquiryId]/page.tsx:20,55,63`); the API allows them to read the quote text (`quotes/routes.py:126-127`, `SalesPlus`) and the database allows them to record a touch (`followups.sql:846`).
* **Viewer**: the quote panel is not loaded at all (`canQuote` is false, `page.tsx:55`), so no control is shown; the API refuses the text (`SalesPlus`), the database refuses the touch (`followups.sql:846`), and the new route answers 403 for a viewer as defence in depth. A viewer can already read a contact's phone through the API and the contacts tab (`crm/routes.py:54`, `page.tsx:338`); this plan neither adds to nor removes that.
* **A quote not yet approved** (draft or rejected): no text is shown (`quote-panel.tsx:117`), the API answers 409 `quote_not_approved` (`service.py:536-541`), and the route and the action both re-check the outcome and refuse (`?whatsapp=not_approved`, and a sentence in the action).
* **A withdrawn or superseded quote**: the outcome is `withdrawn` or `superseded` (`service.py:170-173`), not `approved`, so no control is offered and the route and action refuse. Nothing is "unsent": a message already sent stays sent, and no per-quote record exists to change (section 4, fact a).
* **An approved quote that has expired**: `valid_until` is shown (`quote-view.tsx:57-58`), but the outcome stays `approved` and the text still renders (`service.py:170-173` and `526-582` read no date); orders do refuse an expired quote (`main.py:232`). Offering a chat with an expired price is a trap, so the plan hides **Open in WhatsApp** and **I sent it** on an expired quote and says "This quote has expired" (section 8, no. 4). Copy stays, as today. "Expired" is decided with the India date, the way the quote's own dates are (the quote engine uses `today_ist`, `services/ai-api/app/quotes/builder.py`).
* **A customer with no phone, no contact, no consent, or blocked**: the page asks the API for the database's own gate reading, `GET /leads/{id}/followup?channel=whatsapp` (`followups/routes.py:106-112`), whose `channels[].blocked` is the gate's closed word (`contact`, `key`, `erased`, `consent`, `unkeyed` or null: `followups/models.py:178-183`). Any non-null word replaces the two WhatsApp controls with a plain sentence in item g's wording (`sent-message-actions.ts:27-47`) and, for `consent`, a link to the consent page, built from ids (`sent-message-form.tsx:71-77`). A lead with no contact at all gets "Add the customer first" (`leads/[leadId]/page.tsx:127-133`). A number that is present but cannot be made into a WhatsApp number (section 8, no. 2) is `bad_number`: "The saved number cannot be used for a WhatsApp link. Check it on the contact. You can still copy the text."
* **Another workspace's quote or an unknown id**: the same plain not-found as everywhere (the export route's `notFound()` on a bad id, `export/route.ts:18`); nothing says whether the quote exists elsewhere.

## 8. Open owner decisions, with my recommendation

1. **Does the number go through a redirect route (B) or sit in a link in the page (A)?** Recommend **B**. It keeps the phone out of every page render, the HTML and any action result, at the cost of one small route. It also makes item f the one place in the web that reads a phone for a purpose other than the contacts table, which should be written down in an ADR addendum (slice 5).
2. **A number with no country code.** This is the open question 2 of `manual-price-quote-plan.md` section 20, and this plan depends on it. Recommend: a number of exactly ten digits starting 6 to 9 is an Indian mobile and gets `91`; a number the person wrote with a `+` or `00` keeps its own code; anything else is `bad_number` and the person can only copy the text. Never guess.
